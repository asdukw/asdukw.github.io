# Design

## Context

见 `proposal.md` 的 Why。设计要迁就的现状：

- 正文 HTML 已经由 `scripts/mdx.ts` 在构建期渲染成字符串，存进 `src/generated/posts.ts` 的 `html` 字段；`src/lib/posts.ts` 直接 import 这个生成物，所以**三篇文章的完整正文已经在入口 bundle 里**（实测 `dist/index-*.js` 650 KB raw / 202 KB gzip）。搜索不需要额外下载正文。
- `scripts/mdx.ts` 的 rehype 链已经用 `rehype-slug` 给标题分配了 id，并把 h2/h3 抽成 `toc`（`{ id, text, level }`）。段落边界可以直接复用 `toc`，不需要重新解析 HTML 结构。
- 列表页 `/post` 的筛选状态全部走 URL（`?tag=` / `?q=`，`useSearchParams`），`?q=` 现在的匹配范围是 `title` / `excerpt` / `tags`。
- 正文字数极少：3 篇、4.8 K 字符纯文本、19 个 h2/h3 段落。所有性能判断都以这个数量级为前提。
- 实测约束：本机 Bun 1.4.4 与 Node 24 的 `Intl.Segmenter('zh')` 只做到部分词级切分（`课件`→`课`|`件`，`待办`→`待`|`办`，`汇总`→`汇`|`总`），不能作为索引的切分依据。

## Goals / Non-Goals

**Goals:**

- 正文可检索，中文不需要空格也能命中。
- 段落级定位 + 文章级聚合，结果能给「为什么匹配」的片段。
- 索引与正文同源同构建，漂移能被 CI 抓到。
- 查询零网络请求，纯静态部署下行为不变。

**Non-Goals:**

- 不加搜索弹窗 / `Ctrl+K` 命令面板 / 独立搜索页（后续 change）。
- 不做同义词、拼音、模糊纠错、搜索建议、结果排序可配置。
- 不改路由、`?tag=` 语义、i18n 前缀规则、prerender、评论。
- 不为「以后可能有几百篇」做提前优化（分片加载、Worker 内检索、远程索引）。

## Decisions

### 决策 1：CJK 用双字 bigram 切分，拉丁按词

`tokenize(text)` 把文本切成两类 run：

```
"把课件增量下载到本地 due.md 每 2 天"
   |                              |
   CJK run 6 字                 拉丁/数字 run
   -> 把课 课件 件增 增量 量下 下载 载到 到本 本地
                                 -> due.md, 2
```

规则：CJK 连续片段取**相邻双字**（长度 1 时取单字），拉丁/数字/`._-` 连续片段小写化为整词。

| 备选 | 为什么不选 |
|---|---|
| lunr / MiniSearch 默认按空白切分 | 中文整段变成单个 token，`课件` 搜不到任何东西 |
| `Intl.Segmenter('zh')` | 实测本机只做到部分词级切分，且结果随 ICU 版本漂移；构建期与运行期可能不一致 |
| 全字 unigram | 召回最优但精度最低，`的`/`是` 会污染评分 |
| 引入结巴类分词器（nodejieba 等） | 多一个原生依赖 + 词典体积，为 3 篇文章不值得 |

bigram 是无字典、确定性方案：「课件」精确命中；「增量下载」切成 `增量`/`量下`/`下载`，只要正文里这两个词相邻出现就能命中。

实现放 `src/lib/tokenize.ts`，**构建期与运行期共用同一份**——分词规则只允许有一个真源。

### 决策 2：构建期只生成「段落纯文本」，倒排索引在运行期建

```
build 期  scripts/build-content.ts
            |
            +-> src/generated/posts.ts     （已有：html + toc）
            |
            +-> src/generated/search.ts    （新增：段落纯文本）
                  [{ postId, lang, anchor, heading, text }]
                          |
                    runtime  useMemo
                          v
            MiniSearch 倒排（tokenize = 决策 1 的函数）
```

生成的只是**数据**（剥了标签的段落文本 + 所属标题 + 锚点），不生成倒排表。理由：

- 剥 HTML → 切段 → 提取文本是纯计算且需要正则，放构建期做一次，运行期零解析成本。
- 倒排索引依赖分词器版本，把它写进生成物等于把「分词规则」冻结进仓库；让运行期用同一个 `tokenize` 现建，规则改动不需要重新生成 19 段数据。
- 19 段的建索引耗时是毫秒级，不值得为它做预热或序列化。

备选「完全运行期从 `POSTS.html` 派生」被否：每次加载都要跑一遍 HTML 剥离与分段，与本站「HTML 在构建期生成，浏览器不编译内容」的既有约定相反，也失去了 CI 漂移检查的抓手。

### 决策 3：段落切分复用 `toc`，而不是解析 DOM

`anchor` 直接取 `toc` 里已有的 heading id。段落边界用「该标题之后、下一个标题之前」的定义，在构建期对 HTML 按 `<h2`/`<h3` 切分即可。

正文第一段（首个标题之前的内容）没有 `toc` 条目，`anchor` 记为 `undefined`，链接退化为文章地址本身。

代码块文本保留（`due.md`、`bb-sync run` 这类查询必须能命中），但剥掉标签后只保留文本。

### 决策 4：`?q=` 原地升级，结果仍是文章行

- 保留 `/post?q=`、`useSearchParams`、语言前缀构造全部现有机制，只把 `filtered` 的来源从「字段包含」换成「搜索命中」。
- 搜索结果按文章聚合：同一篇文章取最高分的 1~2 个段落，第一个作为片段。片段从命中词位置前后截取固定窗口（约 40/60 字符），加省略号。
- `?tag=` 与 `?q=` 继续叠加（先按 tag 过滤，再按搜索过滤），不改变现有「筛选条件都在 URL 里」的模型。
- 语言选择复用 `getPosts(lang)` 的既有语义：搜索只在当前界面语言选出的那批文章里匹配，因此同一篇文章的中英版本不会同时出现，缺英文正文时自然回退中文正文——**不在搜索层重实现语言规则**。

### 决策 5：MiniSearch，静态导入

- 选 MiniSearch 而不是 lunr：`tokenize` / `processTerm` 是官方选项，字段加权（`title` 4 : `正文` 2）和前缀匹配开箱即用；lunr 的中文支持要靠插件，且同样要自己写切分。
- 最初打算用动态 `import("minisearch")` 让 `bun build` 拆出独立 chunk。**实测否决**：`bun build --target browser --minify` 对动态 import 不拆分（单个 entry 只产出一个 18.11 KB 的文件），动态 import 只会把 API 变成异步（多一套 loading 状态、多一类击键竞态），换不到任何体积收益。
- 最终：静态导入，体积代价实测 +13.0 KB gzip（入口 chunk 202.1 KB → 215.1 KB，+6.4%）。相对这个基线接受内联，不让搜索引擎的异步化渗透到列表页的状态管理里；本站的既有约定也是「没有网络请求、没有 loading 状态」。
- 以后若要削减这 13 KB，方向是「搜索入口按需加载」（弹窗/独立页），不是把查询改成异步。

### 决策 6：空查询不建索引

`q` 为空或全空白时不触发索引构建，直接返回完整列表；这与 spec 里「空白视为无筛选」一致，也避免首页/列表页首次渲染付建索引成本。

## Risks / Trade-offs

- **bigram 召回噪音**：`的`、`是` 这类单字会成为 token，拉高长尾命中 → 靠停用字过滤 + 字段加权压制；19 段的语料下噪音有限，不引入完整停用词表。
- **3 字以上词的精度下降**：`增量下载` 依赖 `增量`、`量下`、`下载` 同时命中，正文若写作「增量地下载」会漏 → 接受；这是无字典方案的固有代价，命中率仍远高于现在的「只搜标题」。
- **生成物体积**：`src/generated/search.ts` 约 5 K 字符纯文本，被打进入口 bundle → 可接受，且与 `posts.ts` 里已有的 13 KB HTML 同量级。
- **构建期与运行期分词不一致**：两处实现漂移会让索引和查询对不上 → 单文件实现 + 类型检查，构建期不重复实现分词（只共享同一个模块）。
- **SSR / smoke 阶段触碰浏览器 API**：`src/lib/search.ts` 与 `tokenize.ts` 必须是纯 JS，不能用 `window`/`document`；`scripts/render-route.tsx` 会走同一条 import 链。
- **旧链接语义变化**：`?q=` 从字段匹配变全文匹配，命中范围只变宽不变窄 → 不构成破坏性变更，不需要迁移。
- **`?tag=` 与搜索叠加后可能出空结果**：文案上区分「筛选无结果」与「搜索无结果」，沿用现有空态组件。

## Migration Plan

1. 生成物 `src/generated/search.ts` 提交入库；`deploy.yml` 增加第三条漂移检查，与 `posts.ts` / `projects.ts` 同等对待。
2. 上线后旧链接行为只会变宽，无需重定向或数据迁移。
3. 回滚：revert 该次提交即可，没有数据库、缓存或外部服务需要清理。

## Open Questions

- 是否要给搜索加 `Ctrl+K` 弹窗（第二入口）——取决于列表页搜索框的实际使用情况，不影响本 change 的 spec 与任务拆分。
- 是否需要维护一份中文停用字表——先上线看结果质量，需要时再加。
