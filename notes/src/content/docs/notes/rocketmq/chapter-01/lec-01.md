## 一句话定位

RocketMQ 是阿里 2012 年开源、2017 年捐给 Apache 的分布式消息中间件。它的设计目标从来不是「通用消息管道」，而是**交易链路**——订单创建、支付回调、库存扣减这类不能丢、不能乱序、需要事务语义的场景。

这一句话能解释后面所有的取舍：为什么它内置事务消息，为什么它坚持顺序写日志，为什么它的队列数要提前规划。Kafka 面向的是日志与流处理，两者优化的方向不同。

## 五个角色

先看全景。应用和消息中间件之间只有两类交互：**问路**和**收发**，而这两件事是由不同组件承担的。

```
                    +----------------------------+
                    |    NameServer x N（无状态）  |
                    |  只做路由注册与查询，不存消息  |
                    +----------------------------+
                        ^                  ^
           注册(30s)     |                  |  查路由(30s)
                        |                  |
        +---------------+--+        +------+-----------------+
        |     Broker       |        |  Producer / Consumer  |
        |  （唯一有状态）    | <----> |    （你的业务进程）      |
        +------------------+  收发   +-----------------------+
                    ^
                    | 只读查询集群信息
             +------+------------+
             | rocketmq-dashboard |  （不在消息链路上）
             +-------------------+
```

注意箭头的方向：**消息本身只走「应用 ↔ Broker」**。NameServer 从头到尾不碰消息，Dashboard 更是连消息链路都算不上。

### NameServer：一个会「过期」的路由表

职责只有两件：

1. Broker 启动后每 30 秒向所有 NameServer 注册自己（集群名、broker 名、地址、topic 配置）。
2. 客户端来问「某个 topic 的消息在哪些 broker 上」。

它**不存消息，也不存持久化元数据**——所有路由信息都在内存里，重启就没了，靠 broker 30 秒内重新注册回来。NameServer 之间也**互不通信**，集群里多个 NameServer 各自持有完整的一份数据，客户端随便连哪个都行。

> [!NOTE]
> 「NameServer 之间不通信」是它和 ZooKeeper、etcd 最大的区别。这也意味着它的数据不是强一致的：某个 NameServer 刚重启，可能还有几十秒看不到最新的 broker 列表。

**为什么不用 ZooKeeper？** 早期 MetaQ 用的就是 ZK。换掉的理由很实际：

| 维度 | ZooKeeper | NameServer |
| --- | --- | --- |
| 架构 | 需要选举，CP | 无状态，各管各的 |
| 运维 | 需要维护 quorum | 加机器就行 |
| 故障影响 | 集群不可用则写不了 | 单个挂掉不影响已连接的客户端 |
| 代码量 | 一个独立系统 | 据说核心只有几百行 |

对「路由表」这种数据来说，可用性远比强一致重要——路由稍微旧几秒，消息最多晚一点到达，但路由表不可写，整个集群就瘫了。

### Broker：唯一有状态的角色

Broker 才是真正干活的：接收消息、写入磁盘、维护消费队列、响应拉取请求。整个 RocketMQ 里**只有它是需要持久化的**，也只有它的故障会真正影响消息收发。

一个 Broker 通常以主从形式部署：

| 配置项 | 取值 | 含义 |
| --- | --- | --- |
| `brokerId` | `0` | 主节点 |
| `brokerId` | `>0` | 从节点 |
| `brokerRole` | `ASYNC_MASTER` | 异步复制，吞吐高，主挂了可能丢一小段 |
| `brokerRole` | `SYNC_MASTER` | 同步复制，主从都写成功才返回，更可靠但更慢 |
| `flushDiskType` | `ASYNC_FLUSH` | 异步刷盘，页缓存攒一批再落盘 |
| `flushDiskType` | `SYNC_FLUSH` | 同步刷盘，写完才算成功 |

这几项组合起来就是「可靠性等级表」。后面 1.2 会专门讲这几种组合分别会丢什么。

Broker 会监听三个端口：

| 端口 | 用途 |
| --- | --- |
| 10911 | 主通道，客户端实际连接的就是它 |
| 10909 | VIP 通道，老版本为减少一次网络跳转设计，新版本基本可以关掉 |
| 10912 | 主从复制通道，单机模式下闲置 |

:::caution[`brokerIP1` 是广告地址，不是监听地址]
采集到的实践里，最容易踩的坑就是 `brokerIP1`。它不是「我监听在哪个地址」，而是「**我告诉别人来连我的地址**」——Broker 注册到 NameServer 时上报的就是这个值，客户端拿到后直接拿它去连。

所以在容器里跑 Broker 时：

- 填 `127.0.0.1` → 宿主机上的应用能连，但同网络里的其他容器会连到它自己
- 填容器名 → 容器之间能连，但宿主机没有到 bridge 网段的路由
- 填 `host.docker.internal` → 宿主机靠 hosts 记录、容器靠内置 DNS，两边都能解析

这个值的正确性不体现在 Broker 能不能启动，而体现在**客户端能不能连上**——排查时要先看 NameServer 里注册的地址，而不是 Broker 的监听配置。
:::

### Producer / Consumer：客户端进程

它们不是独立服务，而是嵌在业务进程里的客户端库。职责分别是「把消息发到正确的 Broker」和「从正确的 Broker 拉消息」。

关键点：**客户端只配置 NameServer 地址，不配置 Broker 地址**。Broker 地址是运行时从 NameServer 问出来的，这就引出了后面「路由缓存」那一节。

### Dashboard：一个可选的旁观者

`rocketmq-dashboard` 是一个独立的 Spring Boot 应用，通过 NameServer 拉集群信息，让你在浏览器里看 topic、消费进度和积压。

它**不在消息链路上**——挂了业务一点事没有。但排查积压时那条往上爬的曲线，比 `mqadmin` 的输出直观得多，所以本地环境通常会带一个。

### 5.x 多出来的两个组件

| 组件 | 作用 | 什么时候需要 |
| --- | --- | --- |
| Proxy | gRPC 入口，给新客户端（`rocketmq-client-java`）用 | 用新协议、或多语言客户端时 |
| Controller | 主备自动切换，替代 4.x 的 DLedger 模式 | 需要故障自动恢复时 |

经典 Java 客户端走的是 remoting 协议，直连 NameServer 和 Broker，**不需要 Proxy**。单机 demo 也不需要 Controller。

## 存储：三个文件分工

这是 RocketMQ 最值得理解的部分。它把「写到哪」和「从哪读」拆成了三种文件。

```
   写入（顺序追加，所有 topic 混在一起）
        |
        v
   +----------------------------------------------+
   |  commitlog：1GB 一个文件，写满换下一个            |
   |  所有消息不论 topic 全写在这一串文件里，顺序追加   |
   +----------------------------------------------+
        |
        | 后台线程按 offset 顺序扫描，分发出去
        v
   +---------------------------+      +---------------------------+
   | consumeQueue              |      | indexFile                 |
   | 每个 topic 的每个队列一份    |      | 按 key / 时间建哈希索引      |
   | 定长 20 字节：              |      | 支持「按消息 key 查消息」     |
   | offset + size + tag hash  |      | 用于排查与补偿               |
   +---------------------------+      +---------------------------+
        |
        | 消费者按位点顺序读
        v
    消费进度（offset）
```

### 为什么不直接扫 commitlog

因为**混写**。所有 topic 的消息按到达顺序挤在同一个日志文件里，一段 1GB 的文件里可能既有订单消息又有日志消息。消费者只想读「topic 是 `seckill-order` 的第 3 个队列」的消息，扫 commitlog 等于全表扫描。

所以多了一层 consumeQueue：它是**逻辑队列**，每项只有 20 字节，记录「这条消息在 commitlog 的哪个位置、有多长、tag 的哈希是多少」。读的时候先查 consumeQueue 拿到偏移，再按偏移去 commitlog 取出实际内容——一次间接寻址，换来顺序写和按主题读两全。

| 文件 | 写的方式 | 读的方式 | 本质 |
| --- | --- | --- | --- |
| commitlog | 纯顺序追加 | 按偏移随机读（已在页缓存里） | 消息本体 |
| consumeQueue | 顺序追加 | 顺序读 | 消息的「目录」 |
| indexFile | 哈希写入 | 按 key 查 | 查询辅助 |

> [!TIP]
> 这个结构和数据库索引的思路一致：数据顺序写，索引负责定位。区别是 RocketMQ 的「索引」极小（20 字节/条），所以哪怕几亿条消息，consumeQueue 也只有几个 GB，可以整体映射进内存。

### 队列数决定了消费并行度

consumeQueue 是按「topic + 队列」组织的，一个 topic 默认 4 个队列。消费时，一个队列同一时刻只能被一个消费者线程消费——所以**队列数就是消费并行度的上限**。

这是很多积压问题的根因：消费者加机器加到了 20 台，但 topic 只有 4 个队列，其中 16 台空转。队列数要么建 topic 时设够，要么走「动态扩队列」再让客户端重新分配。

## 一条消息的一生

把上面的组件串起来看完整流程：

```
 1. Producer 首次发往 topic X
      |
      +-> 本地路由缓存里没有 X，阻塞向 NameServer 查询（有超时）
      |
 2. 拿到 broker 列表 + 队列列表，缓存在内存
      |
 3. 按规则挑一个队列（轮询 / 哈希 / 随机）
      |
 4. 直连 Broker 发送（此后不再问 NameServer）
      |
 5. Broker 写入 commitlog（建页缓存）
      |        按 flushDiskType 决定什么时候真正落盘
 6. 后台 ReputMessageService 把新消息分发到 consumeQueue 和 indexFile
      |
 7. Consumer 按队列拉取，从 consumeQueue 拿到偏移
      |
 8. 按偏移从 commitlog 读消息体，投递给业务
      |
 9. 消费成功，提交消费位点（offset）
```

三个值得注意的点：

- **第 1 步是阻塞的**。冷启动后第一次发某个 topic，会有一次同步查询的延迟；之后都走缓存。
- **第 5 步不是「一条一条刷盘」**。异步刷盘下消息先进页缓存就返回成功，真正的落盘由后台线程批量完成——这正是「异步刷盘可能丢消息」的来源。
- **第 6 步是异步的**。消息写进 commitlog 之后，要等 Reput 线程把它分发到 consumeQueue 才对消费者可见。正常情况下是毫秒级，但积压严重时会成为瓶颈。

## 客户端路由：为什么是 30 秒

前面的流程里有一处容易误解：客户端是「问一次 NameServer」还是「一直问」？

答案是**缓存 + 定时刷新**，而且发消息这件事本身从不查 NameServer：

```
   本地路由缓存  --首次/未命中-->  NameServer（同步查询）
        |
        | 命中后直接挑队列发往 Broker
        v
     Broker

   后台定时任务：每 30 秒问一次「这个 topic 的 broker 变了吗」
```

三个 30 秒构成了整套「谁还活着」的节奏：

| 行为 | 默认间隔 |
| --- | --- |
| 客户端刷新路由（`pollNameServerInterval`） | 30s |
| 客户端向 Broker 发心跳（`heartbeatBrokerInterval`） | 30s |
| Broker 向 NameServer 注册 | 30s |

为什么不问一次就够？因为路由会变：broker 重启换了地址、新 broker 上线要做迁移、某个 broker 挂掉。只问一次意味着应用会一直往死地址发包。

为什么不是每次都问？因为发送路径上多一次网络往返，吞吐直接腰斩。**用缓存换吞吐，用轮询换正确性**，代价是中间那 30 秒的弱一致窗口。

:::caution[这个 30 秒窗口会骗人]
把 Broker 停掉之后，应用**不会立刻报「连不上」**。它还在用缓存里的旧地址重试，表现是一串发送超时（默认 3 秒）的慢请求，而不是明确的连接错误。

排查现象时要记得：`连接超时` 不代表应用没配置对，可能只是它还在等路由刷新。

另外，路由缓存**只在内存里，不落盘**。所以进程重启后如果 NameServer 不可达，第一次发消息会直接失败——不会「用上次的地址凑合发」。
:::

## 和 Kafka 的边界

两者都是「顺序写日志 + 消费者按位点读」，但优化的目标不同：

| 能力 | RocketMQ | Kafka |
| --- | --- | --- |
| 事务消息（本地事务 + 消息一致） | 原生支持，含回查 | 事务面向流处理 EOS，不是业务事务消息 |
| 延迟 / 定时消息 | 原生支持 | 需外部实现或简单的时间轮 |
| 消息回溯 | 按时间戳重置位点 | 按 offset / 时间都有，更灵活 |
| 队列数 | 建 topic 时定，决定了消费并行度 | 分区可扩容，但有 rebalance 代价 |
| 典型场景 | 交易、订单、支付 | 日志、流处理、数据管道 |

一句话概括：**要事务和延迟就 RocketMQ，要大吞吐和多消费者生态就 Kafka**。说「Kafka 也能做订单」当然没错，但事务消息那套回查机制得自己补。

## 本地最小可用形态

把上面的角色落到容器上，一个够用的本地环境是三个容器：

| 容器 | 角色 | 宿主机端口 |
| --- | --- | --- |
| `rocketmq-namesrv` | 路由注册中心 | 9876 |
| `rocketmq-broker` | 消息存储与收发 | 10911 / 10909 / 10912 |
| `rocketmq-dashboard` | 只读控制台 | 8180（容器内 8082） |

验证环境是否真的可用的顺序，比「容器是否 Up」更有意义：

```bash
# 1. Broker 是否已注册到 NameServer（不是看端口通不通）
mqadmin clusterList -n 127.0.0.1:9876

# 期望看到 broker 名、brokerId、以及它上报的地址
# brokerIP1 配错时，这里显示的地址就是错的，客户端会照着它去连
```

> [!NOTE]
> `docker compose ps` 显示 healthy 只能说明进程活着。Broker 的 healthcheck 最好直接查 `clusterList`，因为「端口开着但没注册成功」是一种真实存在的中间状态。

## 小结

记住四句话就够了：

1. **NameServer 不存消息**，它是内存里的路由表，broker 每 30 秒来刷新一次。
2. **Broker 是唯一有状态的组件**，消息顺序写进 commitlog，靠 consumeQueue 做逻辑索引。
3. **客户端只配 NameServer 地址**，拿到路由后直连 Broker，路由每 30 秒刷新一次。
4. **队列数决定消费并行度**，积压加机器之前先看队列够不够。
