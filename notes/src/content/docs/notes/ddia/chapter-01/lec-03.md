多台机器通过网络通信构成的系统叫**分布式系统**（*distributed system*），其中每个进程是一个**节点**（*node*）。选择分布式通常出于这些原因：

- **固有分布式**：两个以上用户各自用自己的设备交互，设备之间只能走网络。
- **服务间传数据**：数据存在一个服务里却由另一个服务处理，就必须过网络。
- **容错与高可用**：机器、多台机器乃至整个数据中心故障时仍要继续运行，就用冗余接管（第 2 章、第 6 章）。
- **可伸缩性**：数据量或算力超出单机，把负载分散到多台机器（第 2 章）。
- **延迟**：用户遍布全球就多区域部署，让每个人连近的服务器（第 2 章）。
- **弹性**：负载时忙时闲，云上可随需求扩缩、只为在用的付费；单机只能按峰值预配。
- **专用硬件**：对象存储用多盘少 CPU 的机器，分析系统用多 CPU 大内存无盘的机器，机器学习用 GPU。
- **法律合规**：数据驻留法规要求本国居民的数据在本国境内存储处理，用户跨多个司法辖区就得把数据分散到多地。
- **可持续性**：作业时间地点有弹性时，挑可再生电力充足、电网不紧张的时候跑，既减碳又便宜。

## 分布式系统的问题

分布式有代价。每个跨网络请求都可能失败：网络中断、服务过载或崩溃、超时收不到响应；超时后我们并不知道对方究竟有没有收到，贸然重试未必安全（第 9 章）。数据中心网络再快，调用另一个服务也远慢于同进程内调函数。处理海量数据时，往往不如把计算搬到数据所在的机器。

节点多不等于更快：某些情况下单机上的简单单线程程序显著胜过上百核集群。分布式系统还很难排查——响应变慢时问题出在哪？这类诊断技术统称**可观测性**（*observability*）：收集执行数据并允许查询，既看高层指标也追单个事件；OpenTelemetry、Zipkin、Jaeger 这类**追踪**（*tracing*）工具记录谁为哪个操作调了哪个服务、每次花了多久。

一致性也是麻烦。数据库提供多种保证（第 6 章、第 8 章），但每个服务各有数据库时，跨服务的一致性就成了应用自己的问题。分布式事务（第 8 章）是可能的手段，却很少用于微服务：它和服务彼此独立的目标相悖，许多数据库也不支持。

所以只要一项工作能在单台机器上完成，通常就比搭分布式简单、便宜得多。CPU 越来越快，内存磁盘越来越大，硬件越来越可靠，加上 DuckDB、SQLite、KùzuDB 这类单节点数据库，很多负载都能留在单个节点上（第 4 章）。

## 微服务与 serverless

最常见的形态是客户端—服务器：客户端发请求、服务器应答，多用 HTTP（第 5 章）。这种思路传统上叫**面向服务架构**（SOA），近年演化为**微服务**（*microservices*）：每项服务用途明确（S3 的用途就是存文件），经 API 向客户端开放，由一个团队维护。

拆开的好处：服务可独立更新，减少团队间协调；各自用符合需要的硬件；实现细节藏在 API 后，服务方可以自由改实现。数据上通常每项服务有自己的数据库、彼此不共享——否则整个库结构都成了 API 的一部分，再也改不动，一个服务的查询还可能拖累其他服务。

代价是复杂度：每项服务都要有部署、扩缩、日志、监控、告警的基础设施，Kubernetes 这类**编排**（*orchestration*）框架提供了底座，因而成了常见部署方式；开发时想测一项服务，还得把依赖都跑起来。API 演化也难：客户端依赖某些字段存在，增删字段就可能让它出错，且往往到预发布或生产才发现；OpenAPI、gRPC 这类描述标准能帮忙管理两端关系（第 5 章）。

微服务主要是用技术解决人员问题——让多个团队不必互相协调也能独立推进。这对大公司有价值；团队不多的小公司里往往是多余开销。

**serverless**，又称**函数即服务**（FaaS），把基础设施管理再外包一层。用虚拟机得自己决定何时启停实例；serverless 由供应商按请求自动分配和释放资源，按使用量而非机器实例计费。为此它常限制函数执行时长和运行时，首次调用还可能冷启动很慢。「serverless」这个名字也有误导性：每次执行仍用一台服务器，只是下次可能换一台。BigQuery 和各种 Kafka 产品也用这个词，表示自动伸缩、按用量计费。正如按量计费取代容量规划，serverless 把按量计费带到代码执行：只为真正运行的时间付费。

## 云计算与超级计算

另一条大规模计算路线是**高性能计算**（HPC），也称**超级计算**（*supercomputing*）。两者有重叠，但侧重与技术不同：

- **用途**：超算做计算密集的科学计算——天气预报、气候建模、分子动力学、复杂优化；云更多承载在线服务与业务数据系统，持续高可用地响应请求。
- **故障处理**：超算跑批处理作业并定期写检查点，节点坏了常直接停掉整个集群、修好再从最近的检查点重算；云服务不能这么干，得尽量不中断。
- **网络**：超算节点间用共享内存和 RDMA，高带宽低延迟，前提是用户互相信任；云里机器与网络由互不信任的组织共享，需要隔离、加密、认证。
- **拓扑**：云数据中心以 IP 和以太网为主，用 Clos 拓扑保证对分带宽；超算常用多维网格、环面，对通信模式已知的负载更好。
- **地理分布**：云允许节点跨区域，超算通常假定所有节点彼此邻近。

大规模分析系统有时也带一些超算特征。本书主要关注必须持续可用的服务（第 2 章）。
