组织最先要回答的问题之一是：内部做还是外包，自建还是购买。通则是核心能力自己做，例行的事交给供应商。软件有两个独立决定——谁来构建、谁来部署——两者都能不同程度外包，构成一条连续谱：一端是完全定制、自己写自己跑，另一端是 SaaS，只通过 Web 界面或 API 使用。

中间是**自托管**（*self-hosted*）的现成软件（开源或商业），由你亲自部署，比如把 MySQL 装到自己的服务器上。服务器可以是自有硬件（**本地部署**，*on-premises*，哪怕实际放在租来的机架里），也可以是云中虚拟机，即**基础设施即服务**（IaaS）。部署方式（比如是否用 Kubernetes）是另一条轴，不在本书范围。

## 云服务的利弊

用云服务本质是把运维外包。是否更便宜省事，取决于已有技能和负载形态：

- 已熟悉该系统运维、负载又可预测（机器数量不剧烈波动），自购机器自己跑往往更便宜；不会运维的系统，买云比从头学、比招人都快。
- 供应商服务众多客户，运维经验更足，可能服务得更好；反过来自运维能针对自己的负载调优，云商不太会为你定制。
- 负载波动大时云最有价值：按峰值配机器会让资源长期闲置，云可随需求增减。分析型负载尤其如此——大查询瞬间拉起大量资源，查完就闲置；日报这类预定义查询能排队平滑，交互式查询越求快波动越大。数据集小时差别不显著。

云服务最大的问题是**失控**：

- 缺功能只能求供应商添加，通常没法自己实现；宕机只能等它恢复。
- 触发缺陷或性能问题很难诊断：自运行软件能拿到操作系统指标和日志，托管服务给不了这些内部信息。
- 供应商停运、涨价或改产品，你只能跟着走，继续跑旧版本通常不可行；许多服务又没有标准 API，切换成本高，这就是**供应商锁定**。
- 必须信任供应商保护数据安全，合规也更难。

但云不会取代所有内部系统：大量老系统诞生在云之前；有特殊需求时（如高频交易对延迟极敏感），内部系统仍不可替代。

## 云原生系统架构

**云原生**（*cloud-native*）指专为利用云优势而设计的架构。原则上任何可自托管软件都能做成托管服务，但按云原生思路从头设计的系统有实打实的优势：同硬件性能更好、故障恢复更快、能迅速调整资源、支持更大数据集。

| 类别 | 自托管系统 | 云原生系统 |
| --- | --- | --- |
| 事务型 / OLTP | MySQL、PostgreSQL、MongoDB | Aurora、Azure SQL DB Hyperscale、Spanner |
| 分析型 / OLAP | Teradata、ClickHouse、Spark | Snowflake、BigQuery、Azure Synapse |

**云服务的分层。** 自托管软件对运行环境要求很低：常规操作系统、文件系统、TCP/IP，少数要 GPU 或 RDMA，可直接跑在 IaaS 实例上——除了开通快、规格多，与物理机无异。云原生的关键是在低层云服务上再建高层服务：**对象存储**（*object storage*，如 S3、R2）保存大文件，API 受限但隐藏了底层机器，自动把数据摊到多台机器上，机器损坏也不丢数据；Snowflake 这样的云数仓又建在 S3 之上。层次越高越专用：匹配就用现成的，否则自行用低层组件拼。

**存储与计算的分离。** 传统上磁盘是持久存储，靠 RAID 在多块盘上做副本容错。云实例也能挂本地磁盘，但通常只当临时缓存：实例故障或为适配负载换规格后就访问不到。替代品是虚拟磁盘（EBS、Azure 托管磁盘、持久磁盘），可卸载再挂到另一个实例；它不是真磁盘，而是另一组机器模拟出的**块设备**（*block device*，块通常 4 KiB）。这让传统磁盘软件能在云里跑，但每次 I/O 实际都是网络调用，对网络异常极其敏感。

所以云原生服务多半绕开虚拟磁盘，直接建在针对特定负载优化的存储服务上。S3 适合长期存数百 KB 到数 GB 的文件；数据库的一行或一个值远小于此，于是云数据库把小值放在独立服务里，把装了很多值的大块写进对象存储（第 4 章）。这就是存储与计算**解耦**（*disaggregated*）：S3 只负责存，要分析就得在外面跑代码，数据必须过网络。云原生系统还常**多租户**（*multitenant*）：同一服务在共享硬件上处理多个客户，利用率更高、也更容易伸缩，但要防止一个客户影响别人。

## 云时代的运维

管服务器端数据基础设施的人过去叫**数据库管理员**（DBA）或系统管理员；DevOps 把开发与运维并入一个团队，共同对后端服务和数据基础设施负责，Google 的实践叫**站点可靠性工程师**（SRE）。职责是可靠交付服务：配置基础设施、部署应用、监控并诊断影响可靠性的问题。自托管的传统工作大量落在单机上——容量规划、开新机器、在机器间搬服务、打补丁。

云服务用 API 把这些机器藏了起来：存储不再给固定容量的盘，而是**按量计费**（*metered billing*），不用提前规划容量，按实际占用付费；个别机器故障时服务仍高可用（第 2 章）。关注点从单机转向服务，DevOps/SRE 更强调自动化、用临时性虚拟机与服务、频繁更新、从事故学习，并保留组织知识。

角色随之分化：基础设施公司专攻面向大量客户可靠交付；云服务客户力求把基础设施投入降到最低，但仍要选服务、集成服务、迁移服务。按量计费消除了传统容量规划，却要求你清楚资源花在哪：容量规划变成财务规划，性能优化变成成本优化。云服务还有**配额**（*quota*）上限，比如并发进程数，得提前规划。供应商和服务越来越多，集成缺标准、往往大量手工。还有些工作无法外包：依赖库的安全、服务间交互、负载监控、故障根因追查。
