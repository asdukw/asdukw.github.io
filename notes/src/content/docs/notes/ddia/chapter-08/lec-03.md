读已提交与快照隔离能防一部分竞态，却防不住写偏差和幻读。而且隔离级别难以理解、各库实现不一、单看代码很难判断是否安全、也缺少检测竞态的工具。研究者的答案始终很简单：用*可串行化*（serializable）隔离。它保证即使事务并行执行，最终结果也与逐个串行执行相同，能防止**所有**竞态。既然这么好，为何不都用？因为实现它有代价。目前主要有三条路线：严格串行执行、两阶段锁定、可串行化快照隔离。

## 实际串行执行

最简单的办法是彻底消除并发：单线程按序每次只执行一个事务，隔离按定义即可串行化。这在 2000 年代才变得可行，得益于两点：RAM 足够便宜、能把活跃数据集放进内存（避免等磁盘），以及人们意识到 OLTP 事务通常很短（长分析查询多为只读，可在串行循环外用快照隔离执行）。VoltDB、Redis、Datomic 采用此法，省去加锁协调开销，有时反而更快，但吞吐受限于单个 CPU 核。

**把事务封装进存储过程**：单线程系统不允许交互式多语句事务（那会把时间耗在应用与数据库的网络往返上）。应用要么只用单语句事务，要么把整个事务代码作为*存储过程*（stored procedure）提前提交给数据库。只要数据都在内存，存储过程就能快速执行、无需等待 I/O。

**存储过程的利弊**：传统上每家数据库各有存储过程语言（PL/SQL、T-SQL、PL/pgSQL），陈旧、缺库生态，且难调试、难版本控制与部署、难监控；数据库对性能更敏感，写得差的过程影响更大；多租户下运行不受信代码还有安全风险。现代实现改用通用语言（VoltDB 用 Java/Groovy，Datomic 用 Java/Clojure，Redis 用 Lua，MongoDB 用 JavaScript）。VoltDB 还要求存储过程具有*确定性*以便在各副本重放，即*状态机复制*。

**分片**：串行执行把写入吞吐限制在单机单核。像 VoltDB 那样分片，让每个事务只读写单分片，就能让每分片各有一个事务线程、吞吐随核数线性增长。但跨分片事务需要协调，要各分片步调一致，远慢于单分片（VoltDB 报告跨分片写入约每秒 1000 次，低几个数量级且不随机器扩展）。能否限制在单分片内，很大程度取决于数据结构——简单键值容易分片，带多个二级索引的数据则很可能需要跨分片协调。

**串行执行总结**：适合每事务短小快速、活跃数据集能装进内存、写入吞吐能由单核处理（或可无跨分片协调地分片）的场景；跨分片事务虽可行却难扩展。

## 两阶段锁定（2PL）

三十年间唯一广泛使用的可串行化算法是*两阶段锁定*（two-phase locking，2PL，也叫强严格两阶段锁定 SS2PL）。注意 2PL 与 2PC 是两回事：2PL 提供可串行化隔离，2PC 提供分布式原子提交。

2PL 的加锁比防脏写严格得多：只要没有写入，多个事务可并发读同一对象；但只要有事务想写，就必须独占——若 A 已读某对象，B 想写则必须等 A 结束；若 A 已写某对象，B 想读也必须等（2PL 不允许读旧版本）。因此写阻塞写、写阻塞读、读阻塞写，而快照隔离是「读不阻塞写、写不阻塞读」，这正是二者的关键区别。2PL 能防止包括丢失更新、写偏差在内的所有竞态。

**实现**：MySQL/InnoDB、SQL Server 的可串行化与 Db2 的可重复读都用 2PL。每个对象一把锁，分*共享模式*（可多事务同持）与*独占模式*：读须先取共享锁，写须取独占锁，先读后写可升级；锁一直持有到事务结束（提交或中止）——第一阶段获取、第二阶段统一释放，故称「两阶段」。大量加锁易死锁，数据库自动检测并中止其一，应用重试。

**性能**：2PL 最大的缺点就是性能——吞吐与响应明显逊于弱隔离，既因加锁开销，更因并发度降低（只要两事务操作可能引发竞态，其中一个就得等）。一个需要读整张表的事务（备份、分析、完整性检查）要取全表共享锁，先等所有写事务结束，又在其读取期间阻塞所有写，实际让数据库长时间无法写入。因此 2PL 的延迟可能很不稳定，一个慢事务或大量加锁的事务就可能拖停全系统；死锁也更频繁，重试要重做全部工作。

**谓词锁**：还必须防幻读。概念上的*谓词锁*（predicate lock）不属于某个具体对象，而属于所有符合某一搜索条件的对象（含尚不存在、未来可能插入的）。读须先取满足条件上的共享谓词锁，写须检查旧值或新值是否匹配任何已有谓词锁。含谓词锁的 2PL 能防各种写偏差、达到可串行化，但检查匹配锁开销很大。

**索引范围锁**：因此多数 2PL 数据库实际用*索引范围锁*（index-range lock，也叫 next-key locking），即谓词锁的简化近似——把条件放宽到更大的对象集合是安全的（如把「123 房间 12–13 点」近似为「123 房间全天」或「12–13 点所有房间」）。它把共享锁附加到相应索引项或索引值域上，别的事务要改同一部分就得等。它不如谓词锁精确、可能锁住更大范围，但开销低得多，是很好的折中；若无合适索引，可退回对整表加共享锁（安全但很慢）。

## 可串行化快照隔离（SSI）

2PL 性能差、串行执行难扩展、弱隔离又易出错，可串行化与高性能是否无法兼得？并非如此：*可串行化快照隔离*（serializable snapshot isolation，SSI）2008 年提出，能以很小的性能代价提供完整可串行化，已用于 PostgreSQL 的可串行化、SQL Server 内存 OLTP、CockroachDB、FoundationDB 等。

**悲观与乐观并发控制**：2PL 是*悲观*的——只要有出错可能就先等待；串行执行更把悲观推到极致。SSI 是*乐观*的——即使有潜在危险也不阻塞，让事务继续跑，提交时再检查是否破坏隔离，若破坏则中止重试。乐观控制在争用严重时表现差（大量事务中止、重试加重负载），但在余量充足、争用不严重时往往优于悲观方案；可交换的原子操作也能降低争用。SSI 建立在快照隔离之上：读都来自一致快照，再额外检测读写之间的可串行化冲突，决定中止谁。

**基于过时前提的决策**：写偏差反复呈现同一模式——事务读取、检查结果、据此写入；但提交时原查询结果可能已被修改，前提不再成立。数据库不知道应用会如何使用查询结果，只能假定「前提一变，写入就可能失效」，因此必须检测事务是否依据过时前提行事。这分两种情况：检测是否读取了过时的 MVCC 对象版本；检测是否有写入影响了先前的读取。

**检测陈旧的 MVCC 读取**：事务从一致快照读时会忽略快照生成时尚未提交的写入。数据库必须跟踪事务何时因可见性规则忽略了其他事务的写入，提交时再检查这些被忽略的写入是否已提交，若是就中止。为什么不在发现时立刻中止？因为若它是只读事务便无风险，且写入者可能最终中止，过早中止会浪费快照隔离支持长只读查询的优点。

**检测影响先前读取的写入**：类似索引范围锁，但 SSI 的「锁」不阻塞、只像警戒线，负责通知相关事务「你读过的数据可能过时」。事务写入时在索引中查找近期读过受影响数据的其他事务并通知它们；谁先提交谁成功，后提交而发现冲突写入已提交的那一方必须中止。

**性能**：需权衡跟踪粒度——细粒度中止精确但记账开销大，粗粒度更快却可能误伤；有些情况可证明结果仍可串行化，PostgreSQL 借此减少不必要的中止。相比 2PL，SSI 的主要优势是事务不必因等锁而阻塞（读不阻塞写、写不阻塞读），查询延迟更可预测；相比串行执行，它不受单核限制（如 FoundationDB 把冲突检测分散到多机）；相比非可串行化快照隔离，它多一层检查开销。中止率显著影响其表现——长期读写事务易冲突中止，因此 SSI 要求读写事务相当短小（长只读事务无妨），但总体上它对慢事务远没有 2PL 或串行执行那么敏感。
