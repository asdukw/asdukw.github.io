只有当事务读取的数据正被并发修改、或两个事务同时修改相同数据时，才会出现并发问题。并发缺陷很难测试发现（只在时序不利时触发），也很难推理。数据库用*事务隔离*向应用隐藏这些问题，可串行化意味着效果等同于串行运行；但可串行化有性能代价，系统普遍采用较弱的隔离，只防范一部分问题。弱隔离导致的竞态绝非纸上谈兵，曾造成巨额损失、破坏客户数据，也可能被攻击者用高度并发的请求刻意触发。

## 读已提交

最基本的隔离级别是*读已提交*（read committed），提供两项保证：读取只能看到已提交的数据（无*脏读*），写入只能覆盖已提交的数据（无*脏写*）。有些数据库还支持更弱的*读未提交*——防脏写却不防脏读。

**没有脏读**：事务的写入要到提交时才对其他事务可见。若无此保证，别的事务可能只看到多行更新中的一部分（如邮件已出现、未读计数还没加），或读到后来被回滚、从未真正提交的数据（导致*级联中止*）。

**没有脏写**：两个事务并发更新同一行时，若前一次写入尚未提交就被后一次覆盖，就是脏写。读已提交会推迟第二次写入，直到第一次提交或中止。它能防止多行更新混杂（如车卖给 Bryce、发票却开给 Aaliyah），但**不能**防止两个计数器递增的竞态——那里第二次写入发生在第一个事务提交之后，不是脏写，结果仍错。

**实现读已提交**：防脏写最常用行级锁（写事务持锁到结束）。防脏读若用同一把读锁，会让长期写事务拖住所有读，损害响应时间；更常见的做法是为每行同时保留旧的已提交值与当前未提交的新值，读事务在提交前只看到旧值。

## 快照隔离与可重复读

读已提交仍会出现*读偏差*（read skew，一种不可重复读）：Aaliyah 转账期间先后查看两个账户，先看到转出后的 400、再看到转入前的 500，仿佛 100 美元凭空消失。备份和长时间分析查询尤其不能容忍这种不一致——若备份期间数据不断变化，备份的不同部分会处于不同时间点，恢复后不一致就被固化。

*快照隔离*（snapshot isolation）让每个事务都从一个*一致快照*读取——只看到事务开始时已提交的全部数据，之后别的事务的修改它都看不到。这对备份、分析等长只读查询是福音。PostgreSQL、MySQL/InnoDB、Oracle、SQL Server 等都支持其变体，Oracle 等甚至把它作为最高隔离级别。

**多版本并发控制（MVCC）**：快照隔离仍用写锁防脏写，但读取不加锁，做到「读不阻塞写，写不阻塞读」。数据库为每行保留多个已提交版本（而非只有两个），因为不同事务要观察不同时刻的状态。以 PostgreSQL 为例：事务启动时拿到单调递增的事务 ID（txid），写入的数据都标记写入者 txid；每行有 `inserted_by` 和 `deleted_by` 字段，删除只是标记、更新内部转成删除加插入；同一行的多个版本存在同一个堆里，组成可双向遍历的链表，垃圾收集在确认无人可见后才清理。

**可见性规则**：事务读取时按事务 ID 判断哪些行版本可见——开始时仍在进行的其他事务的写入一律忽略；比当前事务更晚启动的事务的写入一律忽略；已中止事务的写入一律忽略；其余可见。因此一行可见需满足：读事务开始时插入它的事务已提交，且它未被删除或删除它的事务在读事务开始时尚未提交。长期事务可一直使用同一快照，数据库从不原地更新，因此提供一致快照开销很小。

**索引与快照隔离**：常见做法是索引项指向某个行版本，查询沿版本链找到对当前事务可见且满足条件的版本；垃圾收集删除不可见版本时也删对应索引项。CouchDB、Datomic、LMDB 则用不可变的写时复制 B 树：每次写产生新根，旧根即天然的一致快照，也需后台压实与垃圾收集。

**命名混淆**：同一技术常被冠以不同名字——快照隔离在 PostgreSQL 叫「可重复读」、在 Oracle 叫「可串行化」；而 PostgreSQL 的可重复读是快照隔离，MySQL 的可重复读却比它更弱。根源是 SQL 标准早于快照隔离、定义含糊，导致「可重复读」几乎说不清是什么意思。

## 防止丢失更新

*丢失更新*（lost update）发生在*读取—修改—写入循环*：两个事务并发读同一值、各自修改、写回，后写者没包含前者的修改，前者的更新就被抹掉。计数器递增、JSON 文档局部修改、两人同时编辑 wiki 整页都可能中招。解决办法：

- **原子写操作**：用数据库内置的原子操作（如 `UPDATE counters SET value = value + 1 WHERE ...`、文档数据库的局部更新、Redis 的原子命令）。能用时通常最佳，但 ORM 很容易让人无意写出不安全的读改写循环。
- **显式锁定**：`SELECT ... FOR UPDATE` 锁住要更新的对象再读改写。可行但需仔细推敲逻辑，易漏加锁，且多对象加锁有死锁风险（数据库会自动检测并中止其一，应用重试）。
- **自动检测丢失更新**：允许循环并行，事务管理器检测到丢失更新就中止并让应用重试。可结合快照隔离高效完成——PostgreSQL 的可重复读、Oracle 的可串行化、SQL Server 的快照隔离都会自动检测（MySQL/InnoDB 的可重复读不会）。
- **条件写入（比较并设置）**：仅当值自上次读取后未变（或版本号未变，即*乐观锁定*）才更新，否则不生效、应用重试。MVCC 下需注意：别的并发事务写入的值虽在快照中不可见，计算 `WHERE` 时通常仍可见。
- **冲突解决与复制**：多主/无主复制下没有唯一最新副本，锁和条件写入不适用，只能允许产生多个*兄弟值*再事后合并。更新可交换（计数器递增、集合添加）时合并可防丢失更新，这正是 CRDT 的思想；而最后写入者胜（LWW）很容易丢失更新，许多复制数据库却默认采用它。

## 写偏差与幻读

还有比脏写、丢失更新更微妙的竞态。医院值班系统要求任何班次至少一位医生在岗：某班次恰有 Aaliyah 和 Bryce 两人，两人几乎同时请假，各自事务都检查「当前至少两人」通过（快照隔离下两次检查都返回 2），于是都退出，结果无人值班。这叫*写偏差*（write skew）：两个事务更新的是**不同**对象（各自的记录），既非脏写也非丢失更新，但如果它们依次运行，第二位就无法退出——只有并发才出错。可把写偏差看作丢失更新的推广：两个事务读取同一组对象，各自更新其中一些（可以不同）对象。

防止手段比丢失更新少得多：单对象原子操作无效（涉及多个对象）；多数快照隔离实现不会自动检测写偏差；可用涉及多对象的数据库约束（唯一、外键等）但「至少一位医生」这类约束大多数库不支持，只能靠触发器或物化视图；若无法可串行化，次优是显式锁定事务依赖的行（`SELECT ... FOR UPDATE`）。更多例子：会议室重复预订、多人游戏两个棋子移到同一格、用户名重复注册、防止余额透支——它们共同点是先 `SELECT` 检查条件，再据结果写入，而写入改变了检查所依据的前提。

若检查的是**不存在**符合条件的行、随后的写入又添加了这样一行，就会出现*幻读*（phantom）：没有具体行可供 `SELECT ... FOR UPDATE` 加锁。快照隔离能防只读查询中的幻读，却挡不住这种读写事务里的写偏差。一种权宜之计是*物化冲突*：人为建一张「房间×时段」表，先锁定对应行再检查、插入，把幻读变成对具体行的锁冲突。但物化冲突难设计、易出错，还把并发控制渗进数据模型，只应作为最后手段——大多数情况可串行化隔离要好得多。
