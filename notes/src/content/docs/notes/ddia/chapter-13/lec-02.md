最抽象地看，数据库、批处理器、流处理器和操作系统做同一件事：存数据、让你处理和查询。Unix 提供的是贴近硬件的低层抽象（管道、字节流文件），关系数据库提供的是高层抽象（SQL、事务，隐藏磁盘结构、并发、崩溃恢复）。哪种更好取决于需求——这两种哲学的张力（NoSQL 可看作把 Unix 式低层方法用于分布式 OLTP）持续至今，本节试图调和二者。

### 组合使用数据存储技术

数据库内置的功能（二级索引、物化视图、复制日志、全文索引）与人们用批/流处理器构建的衍生系统有诸多相似。运行 `CREATE INDEX` 时，数据库扫描一致快照、取出字段排序、写出索引、再处理积压写入、此后随事务持续更新——这与设置新追随者副本、引导 CDC 极其相似：每次建索引都是重新处理现有数据集、把索引衍生为既有数据上的新视图。由此看，整个组织的数据流就像一个巨大的数据库：批/流/ETL 像维护索引和物化视图的子系统，衍生系统像不同种类的索引，只是能力不再由单个集成产品提供，而由不同机器上、不同团队管理的各种软件提供。

组合不同存储与处理工具有两条途径：*联合数据库*（federated database / polystore）提供统一查询接口（如 PostgreSQL 外部数据封装器、Trino），延续关系模型传统、解决跨系统只读查询，但实现复杂；*分拆数据库*（unbundling）则像把数据库的索引维护功能拆出来，让它跨不同技术同步写入，遵循 Unix 传统（小工具各做一件事、通过低层 API 通信、用 shell 组合）。

**让分拆行得通**：联合与分拆是一枚硬币两面，但让多系统写入同步更难。传统靠跨异构系统的分布式事务，问题重重；单个系统或流处理内部的事务可行，但跨技术边界时，带幂等写入的异步事件日志稳健实用得多。基于日志的集成有巨大优势——*松散耦合*：系统层面，异步事件流使系统更能抵御个别组件中断（慢消费者有日志缓冲、故障修复后可追赶、故障被限制在局部，而分布式事务的同步交互常把小故障放大）；人员层面，使不同团队能独立开发维护各自组件，接口足够强（事件的持久性与顺序）又足够通用。

**分拆式与集成式系统**：分拆不会取代数据库（流处理器需要数据库维护状态，输出也需数据库提供查询）；运行多种基础设施有学习、配置、运维成本，应尽量少增加活动部件。对特定工作负载，单一集成产品可能性能更好、更可预测。分拆的目标不是与单个数据库比特定负载性能，而是组合多个数据库、在更广的负载范围取得良好性能——追求广度而非深度。若有一种技术满足全部需求，直接用它是最好选择；只有没有单一软件能覆盖全部时，分拆与组合的优势才显现。

### 围绕数据流设计应用

底层数据一变就更新衍生数据，这个想法不新——电子表格早就有强大的数据流编程能力：公式依赖的输入一变，结果就自动重算。我们希望数据系统在系统层面也如此：一条记录变化，其所有索引、缓存视图、聚合并发刷新，而你不必操心细节。今天的数据系统要向 VisiCalc 学习，还要额外满足容错、可伸缩、持久、集成异构技术、复用库与服务。

**应用代码作为衍生函数**：数据集从另一个衍生需经某种转换函数——二级索引（取字段排序）、全文索引（语言检测、分词、词干化、拼写纠正、同义词、建倒排）、机器学习模型（特征提取与统计分析）、缓存（按 UI 展示形式聚合）。标准化套路可由数据库内置（如 `CREATE INDEX`），依赖具体应用的（如特征工程）则需自定义代码，而这恰是许多数据库难以应付的（触发器、存储过程、UDF 多少像事后补上的）。

**分离应用代码与状态**：数据库并不适合当任意应用代码的部署环境（依赖管理、版本控制、滚动升级、监控、集成都不擅长），而 Kubernetes、Docker、YARN 等专为此设计。趋势是把无状态应用逻辑与状态管理（数据库）分开——既不把应用逻辑放进数据库，也不把持久状态放进应用。这种模型里数据库像可网络同步访问的可变共享变量；但大多数语言无法订阅变量变化、只能轮询，数据库也继承了这种被动方式（订阅变更才刚成为功能）。

**数据流：状态变更与应用代码的相互作用**：从数据流角度思考应用，意味着重新协商应用代码与状态管理的关系——把数据库从被动变量变成对状态、状态变更及处理变更的代码之间相互作用的关注。分拆数据库就是把这一想法用到主库之外的衍生数据集。维护衍生数据需要「状态变更顺序重要」与「容错必不可少」，基于日志的消息代理能提供这些，且开销比分布式事务小得多、运维更稳健。流算子像 Unix 管道一样可组合，围绕数据流构建大型系统。

**流处理器与服务**：主流是拆成服务、用 REST 同步通信；流算子组合与微服务相似，但通信机制不同（单向异步消息流 vs 同步请求/响应）。数据流方法性能更好、更稳健——例如货币换算，微服务要在购买时查汇率服务，数据流则预先订阅汇率更新流、在本地记下当前汇率，处理购买时只查本地库。「最快、最可靠的网络请求就是根本不发请求」。这种连接依赖时间（重处理购买事件需用当时的历史汇率），时间依赖连接仍有开放问题，但围绕数据流构建应用很有前景。

### 观察衍生状态

写路径：信息写入后经多轮批/流处理最终更新所有衍生数据集（数据一到就做，不管有没有人看）。读路径：处理用户请求时从衍生数据集读取、处理后返回。写路径像立即求值、读路径像惰性求值；衍生数据集正是两者相遇之处，代表写入时工作量与读取时工作量之间的权衡。全文索引就是一例：没有索引则写路径省事、读路径昂贵（扫描所有文档）；预计算所有查询则读路径省事、写路径不可能；折中是只为常见查询预计算结果（缓存/物化视图）。缓存、索引、物化视图的作用很简单：移动读写路径的边界，用写入时多做一些来节省读取开销。

**有状态、可离线的客户端**：现代单页 Web 应用与移动应用可在设备上保存大量状态、多数交互无需往返服务器；可把设备上的状态视为服务器状态的缓存，屏幕像素是客户端模型对象的物化视图，模型对象是数据中心状态的本地副本。

**将状态变更推送给客户端**：传统网页加载后不会得知服务器数据变化，浏览器中状态是陈旧缓存（除非轮询）。EventSource、WebSocket 让服务器能主动推送变更，把写路径延伸到最终用户；设备离线收不到通知的问题，可用基于日志代理的消费者重连机制解决——每台设备就是一条小型事件流的订阅者。

**端到端事件流**：React、Elm 等在有状态客户端上做得很好，进一步让服务器把状态变更推入客户端事件管道很自然。状态变更可沿端到端写路径流动（从一台设备触发、经事件日志与流处理器、到另一台设备 UI），延迟可低于一秒。挑战在于无状态客户端与请求/响应假设已深嵌于数据库、库、框架、协议——多数存储支持一次请求一次响应，能订阅变更的很少。要延伸写路径到最终用户，须从请求/响应转向发布/订阅数据流。

**读也是事件**：存储是写路径与读路径的边界（允许随机访问读，否则读要扫描整条日志）。也可以把读取请求表示成事件流：读写都送入流处理器，处理器通过输出流响应读事件——这实际上是在读查询流与数据库之间执行流表连接。一次性读取穿过连接算子后即被忘掉，订阅则是持久连接、不断匹配过去与未来事件。记录读事件还有助于追踪因果与数据溯源（重建用户决策前看到什么），代价是存储与 I/O 开销。

**多分片数据处理**：只涉及单分片的查询，用流发查询小题大做；但对需组合多个分片数据的复杂查询（如统计看过某 URL 的人数、综合多套信誉库评估欺诈），可借流处理器已有的消息路由、分片与连接基础设施分布式执行（如 Storm 的分布式 RPC）。若数据库原生支持多分片连接，直接用可能更简单；但把查询视为流仍是一种逼近大规模方案能力极限的选择。
