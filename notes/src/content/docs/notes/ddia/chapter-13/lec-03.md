无状态服务出问题修复重启即可；数据库等有状态系统设计目标是近乎永久保存信息，出错影响也可能永久持续，因此必须更仔细地思考正确性。四十年来事务属性一直是构建正确应用的首选，但这套基础并不牢固（弱隔离的困惑即一例）；某些领域已彻底放弃事务、改用性能更好但语义混乱的模型。判断应用在特定隔离级别或复制配置下是否安全非常困难，Jepsen 实验就揭示了产品宣称的保证与其实际行为之间的巨大差距。事务方法不会消失，但要既正确又抗故障，事务并非最终答案。

### 数据库的端到端原则

应用用了强安全属性的数据系统，不等于不会丢数据或损坏数据——应用缺陷写入错误数据或删数据，可串行化也救不了。这正是支持不可变、仅追加数据的一条理由：别让错误代码有摧毁正确数据的能力。

**恰好一次执行操作**：处理消息出错时可放弃（丢数据）或重试（可能重复处理两次）。重复处理也是数据损坏（重复收费、计数器多加）。*恰好一次*语义就是让计算即使重试，效果也与从未故障相同。最有效的方法之一是让操作*幂等*，但改造非幂等操作要额外元数据（如已用操作 ID 集合）并在切换节点时用栅栏机制。

**抑制重复**：这种模式到处都有。TCP 用序列号排序、去重，但只在单条连接内有效。事务与连接绑定：客户端发出 `COMMIT` 后、未收到响应前网络中断，就无从知道事务是否提交（图 9-1）。重试已超出 TCP 去重范围——非幂等的转账可能实际转了两次。2PC 打破了连接与事务一一对应，但也不足以保证只执行一次：还要担心最终用户设备与应用服务器之间的网络（HTTP POST 超时后用户手动重试，去重机制无济于事）。

**唯一标识请求**：要让请求跨多跳仍幂等，只靠数据库事务不够，必须端到端考虑。可为请求生成唯一 ID（如 UUID）放进表单、或对表单字段算哈希得到请求 ID；重复提交携带同一 ID，把它一路传到数据库、用唯一约束保证同一 ID 只执行一次。即使隔离级别较弱，关系库通常也能正确维护唯一约束。此外 `requests` 表可作为事件日志（事件溯源/CDC），账户余额更新可作为冗余状态由下游从请求事件衍生，只要事件恰好一次处理即可。

**端到端原则**：Saltzer、Reed、Clark 1984 年提出——只有借助通信两端应用的知识与协助，某项功能才能完整正确地实现，不可能把它作为通信系统本身的功能（不完整版本可提升性能）。本例中「功能」是重复抑制：TCP、数据库事务、流处理器自身都无法彻底排除用户重复提交，需要端到端方案（让事务标识从客户端一路传到数据库）。同理，检查数据完整性、加密都需要端到端措施。低层功能有用（降低高层出错概率），但仅靠它们不足以保证端到端正确。

**在数据系统中应用端到端思维**：应用用了强安全属性的数据库，不代表一定不丢数据；应用自身也必须采取端到端措施。遗憾在于容错机制很难正确实现，若能把高层容错封装成抽象让应用不必操心最好，但似乎还没找到合适抽象。事务曾是这种抽象（把并发、约束、崩溃、网络、磁盘故障压缩成提交或中止），仍不够：代价高，跨异构存储尤甚；不用它就得在应用代码里重新实现容错，而并发与部分失效难以正确推理。因此值得探索既有应用特有的端到端正确性、又能大规模保持性能与运维特性的容错抽象。

### 强制约束

只要把请求 ID 从客户端一路传到数据库，就能端到端去重。那其他约束呢？尤其*唯一性约束*（用户名/邮箱唯一、文件不重名、座位不重复预订），以及账户余额非负、库存不超卖、会议时间不重叠等，强制唯一性的技术通常也适用。

**唯一性约束需要共识**：分布式下强制唯一性需要共识——多个相同值的并发请求，系统必须决定接受哪个、拒绝其余。最常见是单领导者作决定（不介意所有请求汇入单节点、且它不故障时可行），Raft 等共识算法解决领导者失效时安全换主、防止脑裂的问题。唯一性检查可按需唯一的值分片横向扩展（请求 ID、用户名哈希路由到同一分片）；但异步多主复制不适用（不同领导者可能并发接受冲突写入），要立即拒绝违约写入就离不开同步协调。

**基于日志的消息传递中的唯一性**：共享日志保证所有消费者以相同顺序看消息（全序广播，等价共识）。流处理器单线程顺序消费某分片消息，若日志按需唯一的值分片，就能确定性地判断冲突操作谁最先出现。例如用户名注册：请求按用户名哈希分片追加；处理器依次读取、用本地库记录已占用名，对可用名记占用并发成功、对已占用名发拒绝；客户端观察输出流等待结果。增加分片即可扩展——这与用共享日志实现共识的构造相同，也适用于许多其他约束，原则是「任何可能冲突的写入路由到同一分片、依次处理」。

**多分片请求处理**：一笔付款可能涉及请求 ID、收款方、付款方三个分片，传统方法需跨三片原子提交，迫使它们与其他事务全序、损害吞吐。用分片日志与流处理器无需跨分片事务也能实现等价正确性：客户端按源账户 ID 把带唯一请求 ID 的请求追加到相应分片；处理器维护（衍生自日志的）源账户状态与已处理请求 ID，对未见过的请求检查余额，够则预留并向源/目标/手续费账户日志分别发出账/入账事件（都带请求 ID）；出账事件回到源账户处理器时按请求 ID 认出已预留的付款并执行、忽略重复；目标与手续费分片各自消费、更新状态并按请求 ID 去重。这里原子性不来自事务，而来自「把初始请求事件原子写入源账户日志」这一操作。要求：同一账户事件严格按日志顺序、至少一次语义、处理器确定性。若采用恰好一次语义更易实现（崩溃重处理时本地状态也回滚）。

### 及时性与完整性

事务系统提交后写入立即可见（严格可串行化）。分拆成流处理多阶段后则不然（消费者异步），但客户端可等待输出流上的消息。这里「一致性」混合了两种需求，值得分开：

- **及时性（timeliness）**：确保用户观察到系统最新状态。陈旧副本导致的不一致只是暂时的，等待重试会消失。CAP 的一致性指线性一致性（及时性的一种强保证），写后读一致性等较弱的及时性属性也有用。
- **完整性（integrity）**：没有损坏——不丢数据、没有矛盾或虚假数据；衍生数据集必须正确反映底层数据。完整性遭破坏是永久的，等待重试无法修复，必须显式检查修复。ACID 里的「一致性」通常指应用特有的完整性，原子性与持久性是维护完整性的重要工具。

一句口号：违反及时性叫「最终一致」，违反完整性叫「永远不一致」。大多数应用中完整性远比及时性重要（信用卡账单延迟对账可接受，但余额算错或钱凭空消失是灾难）。

**数据流系统的正确性**：ACID 事务同时提供及时性与完整性，因此在事务语境下二者区别无关紧要；而基于事件的数据流系统把二者解耦了——异步处理默认没有及时性保证，但完整性是核心（恰好一次/等效一次就是维护完整性的机制）。可靠流处理无需分布式事务与原子提交也能保持完整性，从而同等正确却性能与运维稳健得多，靠组合：把写入表示成可原子写入的一条消息（适合事件溯源）、用确定性衍生函数派生出所有其他状态更新（类似存储过程）、让客户端生成的请求 ID 贯穿所有层次（端到端去重与幂等）、让消息不可变并允许重处理（易从缺陷恢复）。

**宽松解释约束**：强制唯一性需共识、通常靠单分片单线程消费，流处理绕不过。但许多真实业务其实允许暂时违反看似硬性的约束：库存不足可补货道歉打折、航班酒店超卖并设补偿、银行收透支费、跨组织结算的不一致靠修正机制。这种纠正错误的变更称*补偿性事务*（compensating transaction）。道歉代价是否可接受是业务决策；若能接受，就不必「写入前检查全部约束」，可以先乐观写入、事后检查，只对难以挽回的操作在执行前验证。这些应用*确实*需要完整性，但*不需要*及时性。

**避免协调的数据系统**：两个观察——(1) 数据流系统无需原子提交、线性一致性或同步跨分片协调，也能维护衍生数据的完整性；(2) 许多应用可接受宽松约束（只要完整性始终维护，约束可暂时违反、稍后修复）。二者结合意味着：数据流系统无需协调即可为许多应用提供数据管理、同时保持强完整性。这种*避免协调*的系统极具吸引力：性能与容错更好，可采用多主、跨数据中心异步复制，任一中心独立运行，只提供较弱的及时性却保持强完整性。可串行化事务仍可用于其擅长的小范围，无需 XA；只在确有需要处（如执行不可恢复操作前强制严格约束）引入同步协调。协调与约束减少了「因不一致而道歉」，却可能增加「因中断而道歉」——可根据需要在两者间找平衡。

### 信任但验证

前面讨论都建立在*系统模型*的假设上（进程会崩溃、网络会丢包，但 fsync 后数据不丢、内存不损坏、CPU 乘法正确）。这些假设大多成立，但现实更像概率问题：规模足够大，小概率事件也会发生——数据可能在内存、磁盘、网络中损坏。软件缺陷也始终是风险，低层校验和抓不到；即便 MySQL、PostgreSQL 这类成熟数据库也有过缺陷（唯一约束、可串行化异常）。应用代码缺陷更多，许多应用甚至没正确使用外键或唯一约束。ACID 的「一致性」假设事务无缺陷才成立。

**不要盲信承诺**：数据损坏迟早似乎不可避免，至少应有办法发现并修复，这就是*审计*（auditing）。成熟存储系统（HDFS、S3）不完全信任磁盘：后台进程回读文件、与其他副本比较、迁移数据以降低静默损坏。想确认数据仍在，必须真正读取检查；也要不时尝试从备份恢复。HDFS/S3 仍假设磁盘绝大多数时候正确，但这不同于假设它*始终*正确。目前采用「信任但验证」持续自审计的系统还不多，未来或见更多*自我验证/自我审计*系统。

**为可审计性而设计**：一个事务修改多个对象后，事后很难看出它意味着什么；即便有事务日志，插入/更新/删除也未必说清*为什么*改。基于事件的系统可审计性更好：事件溯源中用户输入是一条不可变事件、所有状态更新由它衍生，衍生确定可重复，同一事件日志用同一版本代码处理必得相同状态。明确表达数据流能让*数据溯源*清晰，完整性检查更可行：可用哈希检查事件存储是否损坏、可重跑衍生流程比对结果、甚至并行跑冗余衍生流程。确定性、定义明确的数据流也便于调试与追踪「系统为什么做某事」——一种时间旅行式调试。

**再谈端到端原则**：若无法完全相信每个组件都不损坏，至少要定期端到端检查数据完整性——覆盖面越广，某阶段的损坏越难逃过。持续端到端完整性检查会增强对正确性的信心，让你行动更快（如自动化测试提高快速发现缺陷的概率，降低变更风险，推动演化）。

**可审计数据系统的工具**：目前少有系统把可审计性当首要目标。一些应用自建审计表，但保证审计日志与数据库状态完整性仍很难；可用硬件安全模块定期签名让事务日志不可篡改，却不能保证一开始进日志的就是正确事务。区块链（Bitcoin/Ethereum）是带密码学一致性检查的共享仅追加日志，交易是事件、智能合约基本是流处理器，共识协议（且拜占庭容错）确保所有节点对同一事件序列达成一致、副本不断互检完整性。对多数应用区块链开销太高，但其中密码学工具可用于更轻量环境：*默克尔树*（Merkle tree，由哈希构成的树）可高效证明某条记录出现在某数据集中；*证书透明性*（certificate transparency）用经过密码学验证的仅追加日志与默克尔树检查 TLS 证书有效性，通过让每条日志由单领导者负责而无需共识。未来这些完整性检查与审计算法或在一般数据系统中更广泛应用。
