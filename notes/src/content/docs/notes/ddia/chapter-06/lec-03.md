单主复制的主要缺点是所有写入都要经过唯一领导者：一旦连不上领导者，就无法写入。*多主复制*（multi-leader，也叫主动/主动、双向复制）允许每个领导者都接受写入，并互为对方的追随者。同步的多主复制等价于单主复制（不过是一个领导者把写入转给另一个执行），因此这里只讨论异步多主复制：某个领导者与其他领导者断开时，它仍能处理写入。

## 跨地域运行

单地区内用多主往往得不偿失，但跨地域部署（geo-distributed / geo-replicated）时它很有用。单主下领导者只能在**一个**地区、所有写入都要绕过去；多主下**每个**地区各有一个领导者，地区内用常规主从复制，地区之间由各领导者互相同步。两者对比：

- **性能**：单主每次写入都要跨互联网发往领导者所在地区，延迟高；多主在本地区处理写入再异步同步，用户感知更快。
- **容忍地区停机**：单主需靠故障切换把别的地区副本提升为领导者；多主各地区可独立运行，恢复上线后自动追上。
- **容忍网络问题**：单主对地区间链路极敏感；异步多主在网络中断时各领导者仍能独立接受写入。
- **一致性**：多主最大的缺点是只能提供弱得多的保证——无法保证账户余额不为负、用户名唯一这类跨领导者的约束，因为不同领导者可能各自处理单独看合法、合在一起却违约的写入。需要这类约束时应选单主。

多主不如单主常见，许多数据库以附加组件形式提供，常有自增键、触发器、约束等配置陷阱，被视为应尽量避开的危险区。

### 多主复制拓扑

*复制拓扑*（replication topology）指写入在节点间传播的路径。只有两个领导者时拓扑唯一；更多时有多种：*全对全*（all-to-all，每个领导者发给其他所有）、*环形*（每个节点从一处收、向另一处发）、*星形*（一个根节点转发，可推广为树）。环形与星形中写入可能经过多跳，节点须转发收到的变更；为避免无限循环，每次写入标记它经过的节点，节点见到自己的标识就丢弃。

不同拓扑各有问题：环形、星形里只要一个节点失效就可能切断其他节点之间的链路；全对全更耐故障，但不同链路速度不一，消息会互相「超车」，导致更新先于它依赖的插入到达——这是因果问题，仅靠时间戳不够，需要版本向量来排序，而许多多主系统并未可靠地做到。

## 同步引擎与本地优先软件

应用需要在断网时继续工作，是另一类多主场景。日历 App 在每台设备上各有一份可写的本地副本，设备之间异步同步，延迟可能长达数小时甚至数天——等于把地区间多主推到极致，每台设备都是一个「地区」。

实时协作（Google Docs、Figma、Linear）同样如此：每个打开的标签页都是一个副本，编辑异步复制给协作者。支持这套过程的库叫*同步引擎*（sync engine）；允许离线编辑的叫*离线优先*（offline-first）；*本地优先软件*（local-first）更进一步，要求即使开发者关掉所有在线服务，协作仍能继续（靠开放同步协议、多家服务商支持，Git 就是一个非实时的本地优先系统）。

同步引擎让客户端持有持久状态、把与服务器的通信移到后台，好处是：本地读取让界面响应极快（追求在 16 毫秒内出帧）、天然支持离线、编程模型更声明式（读写几乎不失败的本地数据，无需处理每次服务调用的错误）、便于配合响应式编程实时反映他人编辑。它最适合「能预先下载用户可能需要的全部数据」的场景；数据量巨大时（如整个电商目录）并不适用。

## 处理写入冲突

多主最大的难题是不同领导者上的并发写入可能冲突，需要解决。两个用户同时把同一页面标题从 A 改成 B 和 C，两次写入各自在本地成功，异步复制时才发现冲突。这里所谓的*并发写入*（concurrent writes）与物理时间是否重叠无关，只取决于一次写入发生时是否知道另一次。

### 冲突避免

最简单的策略是从源头避免冲突：保证某条记录的所有写入都走同一个领导者（如按用户把请求固定路由到某地区）。但只要允许改变指定领导者（地区故障、用户迁移），切换期间就可能冒出冲突。另一个例子是用自增 ID 时让一个领导者只出奇数、另一个只出偶数。

### 最后写入者胜（丢弃并发写入）

给每次写入附时间戳、总取最大者，即*最后写入者胜*（LWW）。这个名字有误导性：并发写入之间本无先后，时间戳顺序实质上随机。它的真正含义是——并发时随机挑一个胜者、静默丢弃其余，副本虽收敛却丢数据。若写入时间戳来自实时时钟，还会对时钟同步极其敏感：时钟快的节点写过的键，后续写入的时间戳可能反而更小而遭忽略。只插入唯一键、从不更新的场景用 LWW 没问题；要更新现有记录，就得掂量丢失更新能否接受。

### 手动冲突解决

不愿随机丢弃，就手工解决（类似 Git 合并冲突）。数据库会保留一条记录的所有并发值，即*兄弟值*（siblings），查询时返回**全部**值，由应用代码或用户合并后写回。问题不少：API 从「一个字符串」变成「一组字符串」，应用代码别扭；让用户手工合并是沉重负担；自动合并若不谨慎会出怪事——亚马逊购物车用并集合并，导致一端已删除的商品又冒出来；多个节点各自解决还可能引入新冲突、结果不一致（B/C 与 C/B 再合并成 B/C/C/B）。

### 自动冲突解决

对许多应用，最好的办法是用算法自动把并发写入合并到一致状态，即保证所有副本*收敛*（converge）：只要处理过同一组写入，状态就相同，与到达顺序无关。针对不同数据类型有不同合并算法：文本可做字符级 diff 合并、集合可跟踪插入与删除（从而正确处理购物车删除）、计数器可分别累加增减、键值映射可按键递归处理。冲突解决并非万能（如列表最多五个元素却并发加了六个，只能丢弃），但它足以支撑许多实用的协作应用。

## CRDT 与操作变换

自动冲突解决常用两类算法：*无冲突复制数据类型*（CRDT）与*操作变换*（OT）。以合并文本「ice」的两处并发插入（开头插 n、末尾插 !）为例：OT 记录插入位置的索引，交换操作后必须根据已应用的并发操作变换索引（把「!」从索引 3 改到 4）；CRDT 不用索引，而给每个字符分配唯一且不可变的 ID，用「前驱字符 ID」定位，同一位置的并发插入按 ID 排序，无需变换即可收敛。OT 多用于文本实时协作（Google Docs），CRDT 多用于分布式数据库（Redis Enterprise、Riak、Cosmos DB）与 JSON 同步引擎（Automerge、Yjs）。

### 什么是冲突？

有些冲突显而易见：同一记录的同一字段被并发设成两个值。另一些很微妙，例如会议室预订系统要求同一房间同一时段只归一组人——两次预订若分别在不同领导者上通过空闲检查，仍可能重叠。这类不变量冲突没有简短答案，第 8 章会给出更多例子，第 13 章再讨论可伸缩的冲突检测与解决。
