前面的分片都要求客户端知道记录的分区键；键值模型最容易做到，因为分区键就是主键的一部分。涉及二级索引就复杂了：二级索引通常不唯一标识记录，而是搜索某个值出现在哪里（某用户的所有操作、包含某词的文章、所有红色汽车）。键值存储通常没有二级索引，但它是关系数据库的基础，也是全文检索引擎的立身之本。二级索引无法干净地映射到分片，主要有两条路线：本地索引与全局索引。

### 本地二级索引

每个分片只维护自己的二级索引，覆盖本分片内的记录，而不管别处（信息检索里叫*按文档分区的索引*）。以二手车网站为例：按车辆 ID 分片，再在 `color`、`make` 上建索引，每新增一辆红车，所在分片就把它的 ID 加进 `color:red` 的倒排列表。

本地索引的好处是写入简单：增删改只需处理包含该记录的那一个分片。读取时，若知道分区键就只查对应分片；若只要部分结果，问任意分片也行。但要拿到**全部**结果又不知道分区键，就必须把查询发给所有分片再合并——匹配记录可能散落各处。这种 scatter/gather 很昂贵，容易出现尾部延迟放大，也限制可伸缩性：加机器能存更多数据，但每次查询仍要所有分片参与，查询吞吐并不会随之提高。尽管如此，本地索引仍被 MongoDB、Riak、Cassandra、Elasticsearch、SolrCloud、VoltDB 等广泛采用。

（若在应用代码里自行维护「值→ID」的映射来实现二级索引，务必保证它与底层数据一致，竞态与部分写入失败很容易让两者失步——这正需要多对象事务。）

### 全局二级索引

另一种是构建覆盖所有分片数据的*全局索引*（global index）。它不能只放在一个节点上（会成为瓶颈），因此索引本身也要分片，而且可以采用与主键不同的分片方式。例如所有分片的红车 ID 都列在 `color:red` 条目下，而索引按颜色值分片（a–r 归分片 0、s–z 归分片 1）。这种索引也叫*按词项分区*（term-partitioned），词项取二级索引中任何可搜索的值。

全局索引以词项为分区键，所以查某个值只需读一个分片就能拿到倒排列表（但要拿完整记录，仍需去读存这些 ID 的各个分片）。缺点是：多条件查询（某颜色且某品牌、同一文本多个词）的词项往往分属不同分片，计算逻辑 AND 时要把很长的倒排列表经网络传输再求交集，可能很慢。

更大的难题在写入：一条记录可能牵动索引的多个分片，二级索引很难与底层数据保持同步。可以用分布式事务原子地更新主记录分片与各索引分片；也可以异步更新（如 DynamoDB 的全局索引），代价是可能读到陈旧结果。CockroachDB、TiDB、YugabyteDB 用全局二级索引，DynamoDB 两者都支持。当读吞吐高于写、且倒排列表不太长时，全局索引仍然很有用。
