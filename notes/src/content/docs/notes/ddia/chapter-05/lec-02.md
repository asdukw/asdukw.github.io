兼容性是编码进程与解码进程之间的关系，要看数据往哪流。常见四种：数据库、服务、工作流、消息。

## 流经数据库的数据流

写库的进程编码，读库的进程解码；只有一个进程时，这相当于给未来的自己发消息，向后兼容是底线。多进程常同时访问，滚动升级期间新旧版本并存，库里的值可能由新代码写入、旧代码读出，因此向前兼容也需要。

**不同时间写入的不同值。** 库允许随时更新，同库里既有五毫秒前、也有五年前写入的值。部署新版几分钟就替换完，库里的数据却不会：不显式重写，旧数据仍以最初的编码躺着，即*数据比代码长寿*。整体重写到新模式叫*迁移*（migration），大数据集代价高昂，多数库尽量避免——加一个默认 `null` 的新列则不必重写，读旧行缺列时填 `null` 即可。模式演化因此让整个库看上去仿佛只有一个模式，底层却混着各历史版本。

**归档存储。** 备份或导入数仓的转储通常统一按最新模式重编码：既然总要复制，不妨让副本一致；快照一次写成、不再修改，适合 Avro 对象容器文件。

## 流经服务的数据流：REST 与 RPC

两个角色：*客户端*（client）与*服务器*（server），服务器公开的 API 叫*服务*（service）。浏览器之外，移动端原生应用与页面里的 JavaScript 也发 HTTP 请求，返回的常是 JSON。服务像数据库，却只接受预先规定的输入输出，这种限制带来封装；微服务的关键目标是服务可独立演化，一项服务一个团队负责，所以新旧版本并存是常态。

**Web 服务。** 以 HTTP 为底层协议即*Web 服务*（Web service），既可服务用户设备上的客户端，也用于组织内互调与跨组织调用（支付、OAuth）。最流行的设计理念是 REST：简单数据格式、URL 标识资源、借 HTTP 做缓存控制与内容协商。客户端得知道端点、格式与响应，服务方用接口定义语言（IDL）定义并演化 API，最流行的是 OpenAPI（JSON）与 gRPC（protobuf）。框架负责路由、缓存、认证等杂事：FastAPI 先写服务器代码再生成 IDL，gRPC 反过来。

**远程过程调用（RPC）的问题。** EJB 与 RMI、DCOM、CORBA、SOAP 都基于 RPC 思想：让远程请求像本地函数调用，即*位置透明性*（location transparency）。它忽略了二者的差别：

- 本地调用可预测；网络请求可能丢失、远端可能很慢，还可能*超时*而无结果，你无从判断发生了什么。
- 重试时原请求可能已经成功、只是响应丢了，除非协议内置去重即*幂等性*（idempotence），操作会执行多次。
- 网络请求慢得多、延迟波动大，参数要全部编码，不能传内存指针。
- 客户端与服务器可能语言不同，框架得在类型间转换，而各语言类型不一致。

没必要强求远程服务像本地对象，REST 的吸引力之一，正是把网络传输视为有别于函数调用。

**负载均衡器、服务发现和服务网格。** 客户端得知道目标地址，即*服务发现*（service discovery）；服务多实例运行，把请求分摊开即*负载均衡*（load balancing）。

| 方案 | 做法与局限 |
| --- | --- |
| 硬件负载均衡器 | 专用设备，客户端只连一个端口，设备转发并探测下游故障 |
| 软件负载均衡器 | 行为相同，Nginx、HAProxy 装在普通机器上 |
| DNS | 域名对应多个 IP；传播慢且有缓存，实例频繁变动时会拿到过期地址 |
| 服务发现系统 | 集中注册表，实例注册元数据并心跳，客户端查表直连；适合动态环境 |
| 服务网格 | 负载均衡器作为客户端库或边车，客户端连本机；加密与可观测性由它承担 |

**RPC 的数据编码与演化。** 服务流可假设先升服务器、再升客户端，于是请求只需向后兼容、响应只需向前兼容。gRPC 与 Avro RPC 按各自格式的规则演化；RESTful API 多用 JSON，增加可选请求参数或响应字段通常算兼容变更。跨组织时服务方控制不了客户端，破坏性变更只能并存多个版本。

## 持久化执行与工作流

一笔支付依次调用欺诈检测、信用卡、银行服务，这一串步骤是*工作流*（workflow），每步是*任务*（task）。*工作流引擎*（workflow engine）决定任务何时何地运行、失败怎么办；Airflow、Dagster 面向 ETL，Camunda 用 BPMN 做图形化定义，Temporal、Restate 主打*持久化执行*（durable execution）。

**持久化执行。** 支付要求恰好处理一次，但中途故障可能扣了款没入账，这两步包不进一个数据库事务。框架提供*恰好一次语义*（exactly-once semantics）：任务失败后重跑，跳过失败前已成功的 RPC 与状态变更——表面上再调一次，实际返回上次结果；前提是把它们记进预写日志（WAL）之类的持久存储。代价是外部服务仍须幂等、调用要带唯一 ID；重放必须按原顺序发出同样的调用，调整顺序就可能出错，改代码要单独部署新版本；重放还要求确定性，随机数与时钟都会惹麻烦。

## 事件驱动的架构

请求在这里叫*事件*（event）或*消息*（message），发送者不等处理完，消息先经*消息代理*（message broker，也叫事件代理、消息队列）。相比直接 RPC：接收者过载时可当缓冲区、崩溃后自动重投、免去服务发现、支持一对多、解耦收发。通信是*异步*的，发送即忘。

**消息代理。** 两种分发模式：*队列*（queue）多个消费者只有一个收到；*主题*（topic）所有订阅者都收到。代理不强制数据模型，消息只是带元数据的字节，编码可用 protobuf、Avro 或 JSON，常配模式注册表，也可用 AsyncAPI（消息版 OpenAPI）规定模式。持久性各异：多数代理写盘、消费后即删，也能配置为永久保留（事件溯源必须如此）。转发到另一个主题时要保留未知字段。

**分布式 actor 框架。** *Actor 模型*（actor model）把逻辑封在 actor 里，各有不共享的本地状态，靠异步消息通信；消息可能丢，但每个 actor 一次只处理一条，不必操心线程。Akka、Orleans、Erlang/OTP 用它把应用扩到多节点，本地与远程用同一套消息机制，跨节点时透明编码。位置透明性在此比在 RPC 里自然，但滚动升级仍要考虑双向兼容。
