内存里的数据是对象、结构体、树，靠指针组织，为 CPU 访问优化；写文件或走网络时，必须摊平成自包含的字节序列。前者到后者叫*编码*（encoding，也称序列化 serialization、编组 marshalling），反向叫*解码*。

应用一改，数据格式也得跟着改，而大系统里代码无法瞬间全量切换：服务端靠*滚动升级*（rolling upgrade）每次只换几个节点，客户端升不升级由用户决定。新旧代码与新旧数据因此长期共存，需要*向后兼容*（backward compatibility，新代码读旧数据）与*向前兼容*（forward compatibility，旧代码读新数据，麻烦得多：旧代码得忽略不认识的字段，并在更新后原样写回，否则数据就丢了）。

## 特定语言的格式

Java 有 `java.io.Serializable`，Python 有 `pickle`，Ruby 有 `Marshal`，还有 Kryo 这类第三方库。省事，但问题很深：与语言绑定，其他语言难读；解码要能实例化任意类，是远程执行漏洞的常见来源；版本管理是事后才想到的；效率同样事后才考虑。除非数据只用一小会儿，通常不是好选择。

## JSON、XML 及其二进制变体

跨语言可读的格式里，JSON 与 XML 最显眼，也几乎同样广受抱怨；CSV 只能表示不带嵌套的表格。文本却有几个麻烦：

- **数字**：XML 和 CSV 分不清数值与纯数字字符串；JSON 分字符串与数值，却不分整数与浮点，也没规定精度。超过 2⁵³ 的整数用 IEEE 754 双精度表示就会失真。
- **二进制字符串**：JSON 与 XML 支持 Unicode 文本，却不支持裸字节序列，惯用 Base64 加模式说明，体积涨 33%。
- **模式**：XML 与 JSON 模式功能强，学习和实现都复杂；不用模式就得把编解码逻辑硬编码。
- **CSV**：完全没有模式，列含义凭约定，增删一列得手工处理。

它们对跨组织交换往往够用——能就格式达成一致，比漂亮高效更重要。

JSON 模式广泛用于 OpenAPI、模式注册表与数据库校验：定义基本类型，再用验证规范加约束。内容模型可开放可封闭，`additionalProperties` 默认 `true`，所以默认在定义“不允许什么”；条件式 `if/else` 与远程引用让它很强，也庞杂难用。

**二进制编码。** MessagePack、CBOR、BSON、Smile 是 JSON 的二进制编码，WBXML、Fast Infoset 是 XML 的。它们扩展了类型（区分整数浮点、支持二进制串），却沿用原数据模型，也不规定模式，字段名照样得写进编码数据：本章那条三字段记录，用 MessagePack 是 66 字节，去掉空白的文本 JSON 是 81 字节——省得有限，牺牲可读性值不值并不好说。

## Protocol Buffers

protobuf 是 Google 的二进制编码库，与 Facebook 的 Thrift 很像。它要求数据有模式，用 IDL 描述（`string user_name = 1`），自带代码生成；模式语言比 JSON 模式简单，只管字段与类型。

同一记录编码为 33 字节。与 MessagePack 一样有类型注解和长度，最大区别是没有字段名，只有数字形式的*字段标签*（field tag），即模式里的 1、2、3。protobuf 把类型与标签塞进同一字节，整数用变长整数编码；`repeated` 表示该字段重复出现，二进制里就是同一标签重复。

**字段标签与模式演化。** 编码记录是各字段编码的拼接，无值字段直接省略，所以标签决定编码数据的含义：字段名可以改，标签号绝不能改，否则已有数据全部失效。加字段就分配新标签，旧代码跳过不认识的标签（类型注解足够算出该跳过多少字节），但必须原样保留未知字段。删字段的考量正好相反。用过的标签绝不能复用，可以标记为保留。类型有些能改，但要防截断：32 位改 64 位，新代码读旧数据没问题，旧代码读新数据会截断装不下的值。

## Avro

Avro 2009 年作为 Hadoop 子项目起步，起因是 protobuf 不适合 Hadoop 的场景。它同样用模式描述结构，有 IDL 与 JSON 两种模式语言，同样只管字段与类型。

关键差异是模式里没有标签号，同一记录只要 32 字节。字节序列中没有任何东西标明字段或类型，纯粹是值的拼接；解析必须按模式中字段出现的顺序逐个读，由模式告知类型——读写双方的模式只要有任何不一致，解码就会错。

**写入者模式与读取者模式。** 编码用自己那版模式，即*写入者模式*（writer's schema）；解码时还用一个*读取者模式*（reader's schema），描述代码期望的字段与类型。两者不同时，Avro 并排比较它们并转换：字段顺序不同无妨，读取者模式没有的字段忽略，缺少的字段填默认值。

**模式演化规则。** 对 Avro，向前兼容是“新模式写、旧模式读”，向后兼容是“旧模式写、新模式读”。只能增删带默认值的字段：新增字段没有默认值，新读取者读不了旧数据，破坏向后兼容；删掉的字段没有默认值，旧读取者读不了新数据，破坏向前兼容。要可空必须用*联合类型*（union type），`null` 还得是第一个分支才能当默认值。改名可借别名，因此向后兼容而不向前兼容；给联合加分支同理。

**写入者模式从哪来。** 不能把它塞进每条记录，否则省下的空间全赔进去。大文件用*对象容器文件*（object container file），模式在文件开头写一次；数据库里每条记录前放版本号，另存模式版本表；双向连接可在建连时协商版本，Avro RPC 如此。

**动态生成的模式。** 没有标签号，模式就能由程序生成：把关系库导出成二进制文件，直接由关系模式生成 Avro 模式，一表一记录、一列一字段，库结构变了重新生成即可。用 protobuf 就得手工分配标签并保证不复用——动态生成不是它的设计目标。

## 模式的优点

protobuf 与 Avro 的模式语言比 XML/JSON 模式简单得多，没有取值范围、正则这类验证规则。思想并不新鲜：ASN.1 早在 1984 年就标准化，DER 编码至今用于 X.509 证书，同样用标签号支持演化。

基于模式的编码的好处：不带字段名，比“二进制 JSON”紧凑得多；模式即文档，解码必须用它，不会与数据脱节；维护模式库可在部署前检查双向兼容；静态类型语言还能生成代码做编译期检查。它给出的灵活性与读时模式相当，保证和工具却更好。
