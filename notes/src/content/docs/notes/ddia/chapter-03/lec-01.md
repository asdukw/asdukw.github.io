数据模型可能是软件开发中影响最深的部分：它不只决定代码怎么写，也决定我们怎么想问题。应用里的模型层层叠加，每层都在用低一层的模型表示自己——对象与 API 之上是 JSON 文档、关系表或图的顶点与边，再往下才是字节（第 4 章）。

最广为人知的是 SQL 采用的*关系模型*（relational model）：数据组织成*关系*（relation，即表），每个关系是*元组*（tuple，即行）的无序集合。Codd 在 1970 年提出，到 80 年代中期已成为规则结构数据的默认选择，此后的竞争者无一长久。2010 年代的 *NoSQL* 留下了*文档模型*（document model）：以 JSON 表示的数据。

## 对象关系不匹配

面向对象语言里的对象要拆成表、行、列，读出来再拼回去，这层转换很笨拙。两种模型的脱节称为*阻抗不匹配*（impedance mismatch），词借自电子学。

ORM（如 ActiveRecord、Hibernate）减少了样板代码，却掩盖不了差异：开发者仍要同时考虑两种表示；它主要服务 OLTP，分析侧仍要面对底层表。最容易踩的是 *N+1 查询问题*——先取 N 条评论，再逐条按作者 ID 查用户表，等于把一次连接拆成 N+1 次查询。

一对多关系未必适合关系形式。领英式简历里姓名放进 `users` 表没问题，职位、教育经历、联系方式数量因人而异，只能各建一表再用外键指回；写成 JSON 文档更贴近应用里的对象。差别在*局部性*（locality）：关系版要多次查询或多路连接，JSON 版一次读取就拿到全部。更准确的说法是*一对少*——职位通常只有几个；若子项成千上万，塞进一个文档就太笨重。

## 规范化、反规范化与连接

用 `region_id` 而不直接写 `"Washington, DC"`，就是*规范化*（normalization）的决定。存 ID 的好处是拼写统一、无同名歧义、改名只改一处；关键在于 ID 对人没有意义，永远不必变，而对人有意义的信息迟早要改，复制多份就得同步更新，漏一处就不一致。代价是读取时多一次查找，由*连接*（join）完成。文档库两种都能存，但通常与反规范化绑定：加冗余字段容易，连接支持很弱，只能先取文档再按 ID 查第二次。

一般规律：规范化写入快、读取慢；反规范化读取快、写入贵，且应视作衍生数据，必须有人负责更新。事务型系统适合规范化，分析系统适合反规范化，到超大规模连接成本才可能成为问题。

社交网络是反例：物化时间线把连接结果预先算好，写入时的扇出（fan-out）就是维持它的手段。但 X 的时间线只存帖子 ID、作者 ID 和少量标记，相当于预存"取关注者最近 1000 条帖子"的查询结果；读时仍要按帖子 ID 取正文、按用户 ID 取名字与头像，这叫*补全 ID*（hydrating IDs）。点赞数与头像变化太快，反规范化进去既不准也不划算——读时需要连接不妨碍高性能，补全 ID 很容易并行。

## 多对一与多对多关系

`positions`、`education` 是一对多；`region_id` 是*多对一*（many-to-one）：许多人住同一地区，而每人只住一个。把组织、学校建成实体后就出现*多对多*（many-to-many）：一个人任职多家组织，一家组织也有多名员工，关系模型用*关联表*（associative table）表示。

多对多很难塞进自包含的 JSON 文档。文档模型让简历的职位引用 `org_id`，指向另一份文档，但两个方向都要查：某人任职过的组织，以及某组织任职过的人。两端都存 ID 是一种反规范化，可能不一致；规范化只存一处，靠*二级索引*（secondary index，第 4 章）支持双向查询——关系模式给 `positions` 的 `user_id` 与 `org_id` 各建索引。

## 星型与雪花型：分析模式

数据仓库通常用关系模型，表结构有几种惯例：*星型模式*（star schema）、*雪花模式*（snowflake schema）、*维度建模*与*一张大表*（one big table，OBT）。

星型的中心是*事实表*（fact table），每行代表特定时刻的一个事件。每项事实单独记一行，为日后分析保留灵活性，代价是事实表可以极大。列分两类：属性（售价、进价，据此算利润率）和指向*维度表*（dimension table）的外键，后者回答事件的对象、内容、地点、时间、方式和原因。连日期也常做成维度表，以便编码公共假期。表通常很宽，事实表超过 100 列不稀奇。

雪花模式是变体：维度再拆成子维度，比如品牌、类别各建一表。它更规范化，但星型更受分析师欢迎。OBT 干脆省掉维度表，把维度信息反规范化进事实表的列，等于预先算好连接，占更多存储，有时查询更快。

星型与雪花主要由多对一关系构成，其他关系为简化查询通常也会反规范化。分析场景里这不太成问题，数据多是不再改变的历史记录。

## 何时使用哪种模型

支持文档模型的论据有三：模式灵活、局部性带来的性能、更接近对象模型；关系模型的回应是连接，以及对多对一、多对多关系的支持。

数据本来就是文档结构（一棵一对多树、通常整棵一起加载）时，文档模型是好选择；拆散到多张表会得到繁琐模式和复杂代码。限制在于无法直接引用嵌套项，只能说"用户 251 职位列表中的第二项"。反过来，需要自定义顺序的场景（待办清单拖拽排序）适合文档模型，按序存进 JSON 数组即可；关系库只能靠整数列重编号或*分数索引*（fractional indexing）。

*无模式*（schemaless）的说法有误导性：读取代码通常假定某种结构，只是数据库不强制。更准确的是*读时模式*（schema-on-read，读取时才解释）与*写时模式*（schema-on-write，写入即校验）。把全名拆成名和姓时，文档库只需开始写新字段、读旧文档时兜底；关系库要 `ALTER TABLE` 加列再对大表跑 `UPDATE`，后者很慢。数据异构时读时模式更合适；若记录结构一致，模式就是强制结构的好机制（第 5 章）。

局部性也有代价：只访问大文档的一小部分，通常仍要加载整份，更新还要重写，所以文档应保持较小。它也不是文档模型的专利：Spanner 允许把子表的行交错嵌套进父表，Bigtable 系*宽列*模型用*列族*（column family）达到同样目的。两者正在融合：关系库加入 JSON 类型与文档内索引，文档库补上连接与二级索引。
