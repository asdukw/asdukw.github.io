本章快速浏览了各种数据模型，篇幅不足以详述每一种，但足以看出一件事：没有哪个模型能通吃。

*关系模型*已有半个多世纪，对许多应用仍是重要选择，尤其在数据仓库与商业分析里——星型或雪花型模式加上 SQL 几乎无处不在。它的几种替代方案则在别的领域流行起来：

- *文档模型*关注自包含的 JSON 文档，文档之间的关系很少，适合一次加载整棵对象树；它换来的是模式灵活与读写局部性。这个模型由 MongoDB、Couchbase 等专用数据库推广，如今大多数关系库也加了 JSON 支持。
- *图数据模型*面对相反的场景：任意事物都可能与其他事物相关，查询要跨越多跳，这类查询用 Cypher、SPARQL 或 Datalog 的递归来表达，而在 SQL 里写同样的事很别扭。
- *数据框*把关系数据推广到列数极多的情形，在数据库与多维数组之间架桥，而多维数组是机器学习、统计分析和科学计算的基础。

模型之间可以互相模拟，比如把图数据放进关系数据库，但结果往往别扭，SQL 对递归查询的笨重支持就是证据：同一个查询在 Cypher 里四行，在 SQL 里要写四段递归。于是每种模型都有专门优化的数据库，提供对应的查询语言与存储引擎；另一方面，数据库也在不断吸收相邻模型：关系库用 JSON 列支持文档数据，文档库补上连接，SQL 对图的支持逐步改善。两边都在向对方靠拢。

*事件溯源*是另一条路：把数据表示为不可变的仅追加日志，适合给复杂业务领域的活动建模——会议报名、座位分配这类状态变化多、规则交织的场景，用事件描述比直接改表更清楚。追加写对写入有利（第 4 章）；为了高效查询，CQRS 把事件日志转换成针对读取优化的物化视图，视图可以随时删掉重放。前提是日志里只有有效事件：请求先是命令，验证通过、执行成功后才成为事实，消费事件的组件不允许拒绝它。代价是重放必须确定，事件不可变也与个人数据删除权冲突。

非关系模型的共同点是不强制模式，应用因此更容易适应变化的需求：加字段、改结构时不必先做大表迁移。但应用通常仍会假定数据有一定结构，区别只在模式是*明确的*（写入时强制，写入即校验）还是*隐含的*（读取时假定）。这也解释了为什么"无模式"的说法有误导性：模式并没有消失，只是从数据库移到了应用代码里；读取代码终究要处理旧格式留下的数据。

还有几类模型没覆盖到：

- 基因组研究需要的*序列相似性搜索*（sequence-similarity search）——在一个充满相似但不相同长字符串的库里找匹配——通用数据库都做不好，所以有 GenBank 这类专用软件。
- 金融系统的复式记账*账本*（ledger）可以用关系库表示，也有 TigerBeetle 这样专攻此道的数据库；加密货币与区块链则把价值转移内建进数据模型。
- *全文检索*（full-text search）算是一种常与数据库配合使用的数据模型，信息检索本身是很大的专业课题，搜索索引与向量搜索只在第 4 章略作展开。
