数据仓库常用关系模型加 SQL，界面上和事务库几乎一样，内部实现却可能完全不同，因为两者优化的查询模式相反。SQL Server、SAP HANA 这类*混合事务/分析处理*（HTAP）产品虽在一个产品里支持两种负载，也逐渐拆成两套独立的存储与查询引擎，只共用 SQL 接口。

## 云数据仓库

新一代*云数据仓库*（BigQuery、Redshift、Snowflake）建立在对象存储与无服务器计算之上，比本地部署的数仓更有弹性，也更容易接上云上的日志摄取与数据处理服务。关键在**存储与计算解耦**：数据放在对象存储，查询算力单独伸缩。

开源侧也在拆解。Hive、Trino、Spark 原先一体化的功能，如今分成四种独立组件：

| 组件 | 职责 | 例子 |
| --- | --- | --- |
| 查询引擎 | 解析 SQL、优化成执行计划、分布式执行 | Trino、Presto、DataFusion |
| 存储格式 | 定义表的行如何编码成文件中的字节 | Parquet、ORC、Lance |
| 表格式 | 定义哪些文件构成一张表，支持增删行与时间旅行 | Iceberg、Delta |
| 数据目录 | 定义哪些表构成一个数据库，负责建表改名删表 | Unity Catalog、Polaris |

表格式之所以必要，是因为 Parquet 写出的文件不可变；数据目录则常独立部署、经 REST 访问。

## 列式存储

事实表往往有上百列、数万亿行，而典型分析查询只碰四五列（分析很少 `SELECT *`）。*面向行*（row-oriented）的存储把一整行的值放在一起，查询仍得把每行上百个属性读进内存、解析、再过滤掉不需要的行。

*面向列*（column-oriented，列式）反过来：把同一列的所有值放在一起，查询只读、只解析自己用到的列。列式布局要求各列按相同的行顺序保存，所以取每列的第 *k* 项就能拼回第 *k* 行。实际上不会把整列连续存放，而是把表切成含几千到几百万行的块，块内再按列存；很多查询只看某个时间范围，于是常让每块覆盖一个时间戳区间，查询只在重叠的块里加载需要的列。

**列压缩。** 一列中不同值的个数通常远小于行数，可以把它转成 *n* 张*位图*（bitmap）：每个不同值一张，每行一位，取该值为 1。位图往往极稀疏，可用游程编码压缩连续同值；Roaring 位图在两种表示间自动选更紧凑的一种。这类位图索引正好匹配数仓查询：`IN` 是几张位图按位*或*，`AND` 是按位*与*——各列行序一致，第 *k* 位对应同一行，所以按位运算等价于行过滤。

别把它和*宽列*（wide-column，或列族）模型混淆：后者一行可有上千列、各行列不同，但同一行的值仍存在一起，是行式存储，Bigtable、HBase 皆属此类。

**排序顺序。** 分别对每列独立排序毫无意义——那样就不知道哪些项属于同一行，排序必须以整行为单位。管理员按常见查询选第一排序键，例如常查「上个月」就把 `date_key` 放首位，查询只需扫描对应范围；第一键相同的行再由第二键排序，让同一天同一产品的记录相邻。

排序还顺带改善压缩：主排序列不同值少，排序后形成很长的连续序列，游程编码即可压到几千字节。效果在第一排序键上最强，越靠后的列越杂乱，收益越弱。

**写入。** 在有序文件中间插入一行非常低效——插入点之后所有压缩列都要重写；批量导入则能分摊重写成本。所以列式存储通常走日志结构路线：写入先进面向行、有序的内存存储，攒够后与磁盘列文件合并，成批写出新文件，旧文件不可变，正适合对象存储。查询要同时检查磁盘列数据与内存中的近期写入并合并结果，这一区别对用户不可见。

## 查询执行：编译与向量化

复杂分析查询会被拆成*查询计划*，其中多个*算子*（operator）可分布到多台机器并行；规划器决定用哪些算子、什么顺序、在哪运行。

在每个算子内部，引擎要对列值做比较与计算。最简单的做法像解释器：逐行遍历，查看查询的数据结构决定比较什么。对数百万行的扫描来说这太慢。实践中两条路：

- **查询编译**（query compilation）：按 SQL 生成执行代码，逐行读取相关列、完成比较，满足条件就把值复制到输出缓冲区，再编译成机器码（常借 LLVM）运行，类似 JVM 的即时编译；
- **向量化处理**（vectorized processing）：仍是解释执行，但成批处理一列中的许多值，调用一组固定的预定义算子。比如把 `product_sk` 列与「香蕉」的 ID 传给相等比较算子，得到一张位图，再与门店条件的位图做按位与，就得到目标门店的香蕉销售。

两者实现差别很大，但都能吃到现代 CPU 的红利：顺序访问内存而非随机访问；把工作放进紧凑的内层循环，让指令流水线保持忙碌；用多线程与 SIMD 并行；直接处理压缩数据，省掉解码、分配与复制。

## 物化视图与多维数据集

*物化视图*（materialized view）是真正写入磁盘的查询结果副本；虚拟视图只是查询的快捷写法，读取时才展开。底层数据一变，物化视图就得更新，代价是写入；换来的是反复执行同一查询时的读取性能。

*物化聚合*（materialized aggregate）对数据仓库尤其有用：许多查询重复使用同样的 `COUNT`、`SUM`、`AVG`，与其每次重算原始数据，不如把常用的聚合缓存起来。*多维数据集*（data cube）把聚合按不同维度排成网格：假如事实记录只引用日期与产品两个维度，就能画成一张二维表，每格是某个「日期—产品」组合下 `net_price` 之类属性的 `SUM`；沿行或列再聚合一次，就得到少一维的汇总。五个维度（日期、产品、门店、促销、客户）原理相同。

优点是某些查询几乎变成查表——要昨天各门店销售额，直接读对应汇总值，不必扫描数百万行。缺点是不够灵活：价格不是维度，就算不出售价超过 100 美元的商品占多大比例。所以多数数仓尽量保留原始数据，只把多维数据集当作部分查询的加速手段。
