前面讲的 B 树和 LSM 树都只对单个属性做范围查询。最常见的多列索引是*联合索引*（concatenated index）：把一列接在另一列后面拼成一个键，连接顺序由索引定义决定。它像老式电话簿——按（姓、名）排列，能查某个姓的所有人，也能查某个姓名的组合，但只想按名字找人时这个索引毫无用处。

*多维索引*（multidimensional index）允许同时约束多个列。地理数据最典型：餐厅网站要找出当前地图矩形内的所有餐厅，也就是同时限定经纬度范围。在经纬度上建联合索引没用，它只能先按纬度收窄（经度任意）或先按经度收窄（纬度可从南极到北极），两者没法同时约束。办法是用空间填充曲线把二维位置映射成一个数再走 B 树，更常见的是 R 树、Bkd 树这类专门的空间索引，它们划分空间，让邻近的点尽量落在同一子树（PostGIS 用的是 R 树）。也可以直接用规则的三角、正方形或六边形网格。

这套机制不只服务地理位置：电商可以在（红、绿、蓝）三维上索引颜色，天气库可以在（日期、温度）上建二维索引，一次找出 2013 年温度在 25～30℃ 的观测；一维索引只能二选一，要么扫全年再筛温度，要么反过来。

## 全文检索

*全文检索*（full-text search）按关键词搜索文本文档，关键词可以出现在任意位置。信息检索是门大学问，还涉及语言相关的处理：中日韩文本词间没有空格，分词要靠模型；拼写错误、词形变化、同义词也都要处理。这些都超出本书范围，但核心原理仍可归到多维查询上：每个可能出现的*词项*（term）是一个维度，文档含词项 *x* 则在该维取 1，否则取 0。搜「红苹果」就是找*红*与*苹果*两维同时为 1 的文档——只是维度数量可能极大。

多数搜索引擎用*倒排索引*（inverted index）回答这类查询：键是词项，值是包含该词项的文档 ID 列表，即*倒排列表*（postings list）。文档 ID 若是连续数字，倒排列表也能表示成稀疏位图——ID 为 *n* 的文档含词项 *x*，就把 *x* 位图的第 *n* 位置 1。要找同时含 *x* 与 *y* 的文档，就是载入两张位图做按位与，与列式数仓里向量化的行过滤是同一招，游程编码下也能高效完成。Lucene（Elasticsearch 与 Solr 的底层）就把词项到倒排列表的映射存在类 SSTable 的有序文件里，再用日志结构方法在后台合并；PostgreSQL 的 GIN 索引同样用倒排列表，还支持对 JSON 文档内部字段建索引。

除了切词，还可以为所有长度为 *n* 的子串建索引，即 *n*-gram：`hello` 的 3-gram 是 `hel`、`ell`、`llo`。这样能搜任意长度不小于 3 的子串，甚至支持正则，代价是索引体积庞大。为容忍拼写错误，Lucene 支持按编辑距离检索（距离 1 表示增删改一个字母）：它把词项集合存成以字符为边的有限状态自动机，结构类似*字典树*（trie），再转成*莱文斯坦自动机*（Levenshtein automaton），从而高效找出距离内的词。

## 向量嵌入

语义搜索不止处理同义词和笔误，还想理解文档讲的概念与查询的意图：帮助中心有一页叫「取消订阅」，用户搜「如何关闭账户」也应当命中。

*向量嵌入*（vector embedding）用嵌入模型把文档变成一串浮点数，表示多维空间中的一个点；语义相近的文档，向量也彼此接近。一篇讲农业的页面可能是 `[0.1, 0.22, 0.11]`，讲蔬菜的 `[0.13, 0.19, 0.24]` 离它很近，讲星型模式的 `[0.82, 0.39, -0.74]` 则很远。真实模型动辄上千维，没人能解释每一维的含义，它只是指向抽象空间某处。距离用余弦相似度（两向量夹角的余弦）或欧几里得距离（空间中两点的直线距离）衡量。这里的「向量」与前述向量化处理无关：后者的向量是一批可被专用代码处理的比特，嵌入的向量是一列浮点数，表示多维空间中的位置。早期的 Word2Vec、BERT、GPT 处理文本，后来扩展到音频、图像与视频，近年还走向*多模态*（multimodal）：同一个模型为多种模态生成向量。

查询时，搜索引擎把查询连同上下文（比如用户位置）交给嵌入模型得到查询向量，再在*向量索引*里找最接近的文档向量。R 树不适合高维，需要专门的索引：

| 索引 | 做法 | 取舍 |
| --- | --- | --- |
| 平面（Flat） | 原样保存所有向量，逐一算距离 | 结果精确，但慢 |
| 倒排文件（IVF） | 把向量空间聚成若干分区（*质心*，centroid），只比探测到的分区 | 快，但近似：邻近向量可能落在不同分区；探测数越大越准也越慢 |
| 分层可导航小世界（HNSW） | 多层图，节点是向量、边表示邻近，从最稀疏的顶层逐层下探 | 同样近似，但查询只需沿边局部游走 |

IVF 与 HNSW 都被主流向量库实现，Faiss 提供多种变体，PostgreSQL 的 pgvector 两者都支持；两者的完整算法细节超出本书范围。
