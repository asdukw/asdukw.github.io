许多问题在单节点上很简单、加上容错就极难：单领导者能提供线性一致性，但它失效时如何避免脑裂地切换？单节点线性一致 ID 生成器只是一个原子计数器，它崩溃了怎么办？单节点 CAS 可能只需一条 CPU 指令，如何让它容错？这些都是同一个基本问题——*共识*（consensus）的不同实例，也是分布式系统中最重要、最基本又最难正确实现的问题之一。最著名的算法有视图戳复制（VSR）、Paxos、Raft、Zab，它们都采用非拜占庭模型（网络可任意延迟丢弃、节点可崩溃重启断开，但都正确遵守协议）。

> FLP 结果证明：只要存在节点崩溃的可能，就没有算法能保证**始终**达成共识。但它针对的是异步模型下的确定性算法（不能用时钟或超时）；只要允许用超时怀疑节点失效（哪怕偶尔出错），甚至只需引入随机数，就能绕过这个不可能性。因此实践中分布式系统通常仍能达成共识。

### 共识的多面性

共识有几种表述：*单值共识*（类似原子 CAS，可实现锁、租约、唯一约束）、*共享日志/全序广播*（可构建状态机复制、单主复制、事件溯源）、*原子提交*（多库多分片事务的全有全无）。这几者彼此等价——有其一即可转换为其他任意一种。

**单值共识**：一个或多个节点*提议*某值，算法从中*决定*一个值。必须满足四条属性：*一致同意*（任意两节点不会决定不同值）、*完整性*（决定后不能改主意）、*有效性*（决定的值必须有人提议过）、*终止*（每个未崩溃节点最终都能决定）。前三条是安全属性，若不关心容错，把某节点硬编码成独裁者即可；困难全在容错——终止是活性属性，要求即使一部分节点永久消失（想象数据中心被山体滑坡掩埋），其余节点仍能作出决定。可证明任何共识算法都要求至少多数节点正常才能保证终止，这组多数即可构成法定人数；即使多数失效，多数算法仍能保证安全属性始终成立。

**比较并设置（CAS）作为共识**：有容错且线性一致的 CAS，就能解决共识——先把对象设为空，各节点调用 CAS 把空改为自己的提议值，对象最终被设成什么，共识就决定什么；反之亦然。线性一致的读写寄存器则**不足以**解决共识（FLP 表明异步崩溃停止模型下确定性算法无法解决共识，而线性一致寄存器可在该模型下用仲裁读写实现）。

**共享日志作为共识**：共享日志支持「请求追加值」与「读取日志」两种操作，须满足最终追加、可靠交付、仅追加、一致性、有效性。有共享日志就能解决共识——每个想提议的节点请求把值加入日志，第一条日志条目中的值即决定值。反之亦可由共识构造共享日志（为每个槽位运行一个共识实例）。

**获取并增加作为共识**：有 CAS 就易实现获取并增加；反之有容错获取并增加能否解决共识？读到零的节点胜出，但其他节点不知谁赢了，胜者若崩溃则其余悬而未决，无法终止——除非提议值节点不超过两个（其*共识数*为 2）。CAS 与共享日志的共识数为 ∞。

**原子提交作为共识**：原子提交要求「任一参与者投中止则必须全部中止」，比共识（可决定任意被提议值）多了*非平凡性*（全投提交且无超时则必须提交）。有共识可解决原子提交（各节点把票广播，收到全部提交票才提议「提交」）；反之有容错原子提交也可解决共识（在法定人数上用 CAS 尝试设值）。

### 共识的实践

理论上这些问题等价，实际中多数共识系统提供*共享日志*（Raft、VSR、Zab 直接提供，Paxos 常用 Multi-Paxos 扩展）。共享日志与复制天然契合：每条日志条目代表一次写入，各副本以相同顺序、确定性逻辑处理，最终状态一致——这就是*状态机复制*（也是事件溯源原理），还能实现可串行化事务（每条日志条目是一个存储过程形式的事务）。它也很容易改造成单值共识、多个单值实例、原子获取并增加、栅栏令牌（如 ZooKeeper 的 `zxid`）。

**从单主复制到共识**：传统单主库把领导者故障切换留给管理员手工操作，停机长、不满足终止。共识要求自动选出新领导者，但这里有个「鸡生蛋」难题——选举领导者需要共识，解决共识又需要领导者。共识算法用*纪元编号*（Paxos 的 ballot、VSR 的 view、Raft 的 term）化解：保证每个纪元内领导者唯一；节点超时未收到现任领导者消息就可能发起投票、取得更大的纪元编号；纪元编号高者说了算。领导者追加下一条日志前要先向法定人数收集选票确认没有更高纪元的领导者。于是需要两轮投票——第一轮选领导者、第二轮对下一条日志条目表决，两轮法定人数必须重叠。这表面上像两阶段提交，实则不同：共识中任何节点都可发起选举、只需一组法定人数响应；2PC 只有协调者能请求投票、且必须每个参与者都同意才能提交。

**微妙之处**：Raft、Multi-Paxos、Zab、VSR 都采用「先选领导者、再对每条日志条目投票」的结构，每条新条目同步复制到法定人数才向客户端确认。差异在细节，例如新领导者必须保留旧领导者已追加的所有条目——Raft 只允许日志至少与多数追随者一样新的节点当选，Paxos 允许任何节点当选但要求先补齐日志。若为提升可用性削弱「新领导者须掌握最新数据」（如 Kafka 的非同步副本选举），就会在故障时轻易丢数据、损坏。多数共识算法假定节点集合固定，实践中扩展出了*重新配置*功能（先加新节点再移除旧节点）。

**利弊**：共识本质是「正确实现的单主复制」——领导者失效自动切换，面对各种故障不丢已提交数据、绝不脑裂。任何提供自动故障切换却没用验证过的共识算法的系统很可能不安全；但用了共识也不保证整个系统一定正确。代价是：总要严格多数节点（容忍 1 个故障至少 3 节点、容忍 2 个至少 5 节点）；每项操作都要与法定人数通信，增加节点反而变慢；网络分区时只有多数派一侧能进展；依赖超时检测失效，跨地域时超时很难调；有些算法（如 Raft）对特定网络问题敏感，可能领导权来回跳转。若既要高可用又不愿付共识成本，只能改用较弱一致性模型（无主/多主）。

### 协调服务

ZooKeeper、etcd、Consul 等*协调服务*尤其倚重共识。它们表面像键值存储，却只保存少量可全放内存的数据（仍写盘保证持久），用容错共识复制到多节点，用途是协调另一个分布式系统中的多个节点（如 Kubernetes 依赖 etcd、Spark/Flink 高可用依赖 ZooKeeper）。以 Chubby 为蓝本，它们把共识与几项实用功能结合：*锁与租约*（用 CAS 实现，多个节点争抢只有一个成功）、*栅栏机制*（单调递增 ID 生成栅栏令牌，ZooKeeper 用 `zxid`/`cversion`，etcd 用修订号）、*故障检测*（长会话+心跳，超时则释放租约，ZooKeeper 的临时节点）、*变更通知*（键变化时主动通知，无需轮询）。

**将工作分配给节点**：选举领导者/主实例、分配分片资源、节点增删时再平衡，都可组合原子操作、临时节点与通知来完成。实现得当可自动从故障恢复。专用协调服务的好处是：无论依赖它的系统有多少节点，它本身只需跑在固定的一小组（通常 3 或 5 个）节点上，把共识「外包」出去比让上千节点共同跑共识高效得多。它管理的数据通常变化缓慢（如分片分配关系几分钟到几小时才变一次），不适合存每秒变化数千次的数据。

**服务发现**：协调服务也常用于服务发现（服务启动时把网络端点注册到注册表）。故障检测与变更通知让客户端易跟踪实例增减。但服务发现用共识往往杀鸡用牛刀——它通常不要求线性一致性，高可用与低延迟更重要，更可取的是缓存服务发现信息、接受略有陈旧（如基于 DNS 的多层缓存）。为此 ZooKeeper 提供不参与投票的*观察者*（observer）节点，其读取可能陈旧，但网络中断时仍可读、也能提升读吞吐。
