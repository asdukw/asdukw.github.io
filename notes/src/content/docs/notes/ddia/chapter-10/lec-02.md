许多应用创建记录时要分配唯一 ID 作主键。单节点自增整数只需 64 位（甚至 32 位，但有风险），还能反映创建顺序。单节点 ID 生成器本身就是一个线性一致系统：每次取 ID 原子地递增计数器并返回旧值，即*获取并增加*（fetch-and-add）；它保证若 A 的消息发布完成早于 B 开始发消息，则 B 的 ID 更大（并发消息只要求 ID 不同，不规定顺序）。

单节点生成器的问题：本身是单点故障；跨地区取 ID 要绕半个地球；高写入吞吐下成瓶颈。替代方案都削弱了顺序保证：*分片 ID 分配*（一节点出偶数、另一出奇数，或预留分片位——但失去顺序含义）、*预分配 ID 块*（节点各领一段区间，同样无法保证顺序）、*随机 UUID*（本地生成无需通信，但 128 位且顺序随机）、*为日历时钟时间戳补充唯一性信息*（时间戳放高位，再填分片号/序列号/随机值，如 UUIDv7、Snowflake、ULID、MongoDB ObjectID）。它们都能生成唯一 ID，但顺序保证远弱于单节点自增。而且基于日历时钟的时间戳至多给出近似顺序（时钟偏差可能让后发生的事件时间戳更小），通常不满足线性一致性。

### 逻辑时钟

物理时钟（日历、单调）度量流逝的秒数；*逻辑时钟*（logical clock）则是计算已发生事件数量的算法——不能告诉你现在几点，却可相互比较判断先后。它通常要求：时间戳紧凑且唯一、任意两个可比较（*全序*）、顺序与因果关系一致（A 先于 B 则 A 的时间戳小于 B）。

**Lamport 时间戳**：每个节点有唯一标识符并维护一个计数器，时间戳是二元组（计数器, 节点 ID）。节点生成时间戳时先递增本地计数器；看到别节点更大的计数器时把本地推进到该值。比较时先比计数器、再比节点 ID，得到与因果一致的全序。

**混合逻辑时钟**（HLC）：Lamport 时钟与物理时间无关（不能查某天的消息）、且不通信的节点计数器可能相差悬殊。HLC 兼顾两者——像物理时钟以秒/微秒计数，又像 Lamport 时钟在看到更大时间戳时向前推进；每次生成也递增，保证单调向前（即使底层物理时钟被 NTP 校正回跳），只要求各时钟大致同步。CockroachDB 就用 HLC。

**与向量时钟的区别**：Lamport/HLC 很适合生成 MVCC 的事务 ID（快照与因果一致），但并发生成的时间戳只被任意定序，单看两个时间戳通常无法判断是并发还是先后。要判断记录是否并发创建，得用*向量时钟*（vector clock），代价是时间戳大得多。

### 线性一致的 ID 生成器

Lamport/HLC 仍弱于线性一致的 ID 生成器：后者要求只要请求 A 在 B 开始前完成，B 的 ID 就必须更大——即使二者从未通信；而 Lamport 时钟只保证新时间戳大于它**见过**的时间戳。反例：用户先把账户设为私密、再用另一台设备上传照片，若两库各用逻辑时钟且照片库计数器略落后，照片上传可能拿到更小的 ID，于是快照读会把本该私密的照片显示出来。最简单的修复就是用线性一致的 ID 生成器，保证照片上传 ID 一定大于账户变更 ID。

**实现**：最简单是用单个节点原子递增并持久化计数器，再用单主复制容错（TiDB/TiKV 的*时间戳预言机*）。可用批量预留避免每次写盘复制——先持久化并复制一批 ID，用完前再预留下一批，崩溃重启或切换可能跳过一些 ID，但绝不重复或乱序。ID 生成器很难分片、也难跨地区分布（分片发号后无法保证全局顺序），好在它工作简单、单节点吞吐很高。也可用 Spanner 式的物理时钟区间（TrueTime）：返回不确定性区间、等区间过去再返回，无需通信即可线性一致排序，代价是需要高度同步的时钟与相应软硬件。

**用逻辑时钟强制约束？** 不够。多个节点争抢同一锁/用户名时，可用逻辑时钟选时间戳最小者，但这只解决一半——节点怎样确定自己的时间戳就是最小？它必须收到**每一个**可能生成时间戳的节点的消息；只要有一个节点失效或失联，系统就停滞，因为谁也无法排除它持有更小时间戳。要以容错方式实现锁、租约等构造，需要比逻辑时钟更强的工具：共识。
