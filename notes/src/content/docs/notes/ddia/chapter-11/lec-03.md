批处理框架处理数据主要有两种模型：MapReduce 与数据流引擎。数据流引擎在实践中已基本取代 MapReduce，但后者影响深远，值得理解。

### MapReduce

其处理模式与日志分析示例很像：读取输入文件并拆成*记录*（如每行）；对每条记录调用 mapper 提取键值；按键排序；调用 reducer 遍历排序后的键值对并合并同键的值。四步可由一个 MapReduce 作业完成——第 1 步由输入格式解析器负责、第 3 步的排序是隐式的（mapper 输出传给 reducer 前总会排序），只有 map 与 reduce 需写定制代码。mapper 每条输入调用一次、可产生任意数量键值对、不保留跨记录状态，因而天然易并行；reducer 收集同键的所有值、可产出输出记录。若需第二个排序阶段，再写一个作业。MapReduce 的编程模型来自函数式编程的 map/reduce，map 与 reduce 可组合、map 天然易并行。缺点是手写复杂作业很费力（连接算法都得自己实现），基于文件的 I/O 无法流水线化，因而较慢。

### 数据流引擎

Spark、Flink 等把整个工作流作为一项作业处理，而非拆成独立子作业。它们显式建模数据流经多个阶段，故称*数据流引擎*：提供底层 API（逐条调用用户函数）与连接、分组等高层算子；按输入分片并行、把一任务输出复制到另一任务。相比 MapReduce 的优点：排序只在必要时执行、连续不变分片的算子可合并、依赖显式声明以便优化局部性、中间状态通常只存内存或本地磁盘（I/O 更少）、算子可在输入就绪后立即执行、可复用进程减少启动开销。因此同样计算往往快得多。

### 混洗数据

排序是批处理的基础：要对无法装入单机的 PB 级数据排序，就需要输入输出都分片的分布式排序算法——*混洗*（shuffle，注意它产生的是有序结果、并非随机）。以 Hadoop MapReduce 为例：每个输入分片启动一个 map 任务；mapper 输出按键哈希写到对应 reducer 的本地文件，并在文件中按键排序（内存有序结构→有序段→逐步合并）；每个 mapper 完成后 reducer 拉取属于自己的有序文件、像归并排序一样合并，使同键相邻；再对每个键调用一次 reducer、传入值迭代器；输出顺序写成每 reduce 任务一个文件，即输出数据集的分片。

**JOIN 与 GROUP BY**：混洗会把同键的键值对集中到同一 reducer，这正是分布式连接的基础。以「活动事件日志 ⋈ 用户数据库」为例：两个 mapper 分别以用户 ID 为键输出页面浏览与出生日期，混洗后 reducer 同时拿到某用户的所有浏览与出生日期，先存下出生日期再遍历事件输出——即*排序合并连接*（sort-merge join），任何时刻内存里只需一条用户记录。下一作业再用 URL 作键混洗、在 reducer 里按年龄段计数，即*分组*与聚合。二次排序（secondary sort）可让 reducer 先看到维度记录再按时间戳看事实记录。

### 查询语言

基础设施成熟到可在上万台机器上处理数 PB 后，焦点转向编程模型。MapReduce、数据流引擎、云数据仓库普遍采用 SQL：代码更少、可交互使用，让分析师等非工程师也能探索数据；查询引擎还能把 SQL 转成批处理作业，借助基于代价的优化器选择连接算法、调整连接顺序以减少中间状态。其他语言仍有专门用途（Pig、JSON 查询语言、图的 Gremlin 等）。批处理与云数据仓库正在收敛：批处理支持 SQL、数据仓库上云并采用相同的调度/容错/混洗技术；但迭代图算法、复杂 ML、多模态 AI 数据等仍难用 SQL 表达，数据仓库也较贵，选型取决于成本、便利、难度与可用性。

### 数据框

数据科学家习惯 R 与 pandas 的*数据框*（DataFrame）模型（类似关系表，按列同类型，用函数做过滤/连接/排序/分组）。早期数据框只在单机内存执行；Spark、Flink、Daft 等为让数据科学家处理大数据集也采用数据框 API。注意本地数据框常带索引且有序，分布式数据框一般没有，迁移后性能可能出乎意料。pandas 调用即执行，Spark 则先把调用转成查询计划、经优化后在数据流引擎上执行。Daft 等同时支持客户端与服务端计算，Apache Arrow 提供共享的列式数据模型。
